# Automator Architecture

Bun workspaces with Turborepo. Application code is TypeScript with strict checking. Each application owns its dependencies, TypeScript configuration, and scripts; shared packages export source directly and Next.js compiles the consumed TypeScript packages.

## Workspaces

- **`apps/web`** — Next.js App Router app, port 3000, the dashboard/builder host (workspace shell, flows, marketplace). Depends on `api-client`, `contracts`, `ui`, `miniapp`, plus `@xyflow/react` (React Flow) and `zustand` for the flow builder under `src/builder/`. Screen-level UI behaviour lives in `docs/web-ui.md`.
- **`apps/runtime`** — Next.js App Router app, port 3002, the host for shared end-user apps: `/a/[flowId]` plays a flow as its mini-app (see Mini-apps below), plus a landing placeholder, error/not-found screens, and a process health endpoint. Depends on `api-client`, `contracts`, `ui`, `miniapp`. Production uses `PORT` when set, otherwise 3002.
- **`apps/ui-lab`** — local Next.js component preview, port 3003. An app-owned sidebar and header surround previews of the installed UI primitives, with a theme toggle and content width presets. Agentation provides dev-only browser annotations without an Agent Sync server. Depends on `ui` only; no API or database dependency, no Railway service.
- **`apps/api`** — Elysia app on Bun, port 3001 (overridable with `PORT`), listening on IPv6 for Railway private networking. `src/config.ts` reads the environment once at startup; production refuses to start when a required variable is missing, while development warns and continues. Depends on `contracts`, `db`.
- **`packages/db`** — Bun SQL connection pool and database health query (`SELECT 1`), timing out after three seconds. The `automator_users` table stores the Privy user ID, profile name, unique lowercase username, and verified embedded EVM wallet address; syncing a user preserves an existing wallet address when Privy reports none. The `automator_flows` table stores each flow's owner (a user, deleted with them), name and description as columns for listing, the graph (`version`, `nodes`, `edges`) as one JSONB document, and created/updated timestamps; the flow store's reads and writes are all scoped to the owner, so another user's flow behaves like a missing one; `findPublished` is the one exception, joining `automator_listings` for the public read, alongside `findForWebhook` (id and token, enabled only) and `listEnabled` (every owner) for the trigger paths; `setEnabled` toggles activation. The `automator_runs` table (`runs.ts`) keeps one immutable row per stored run: owner, flow (cascade), status, the executed document snapshot and the `FlowRun` result as JSONB, the `source` that started it, and start/finish timestamps, indexed per owner and per flow by start time; `latestStartedAt` serves the scheduler. The `automator_listings` table holds marketplace listings: a unique slug, the source flow (one listing per flow, deleted with it), the owner, name, a description of at most 280 characters, a JSONB snapshot of the graph, the highlighted node types, a fork count, and publish/update timestamps; the listing store reads join the owner for the byline, its writes are owner-scoped, and forking inserts the snapshot as a new flow and counts it in one transaction. `account.ts` reads per-owner counts across these tables (flows and enabled flows, runs started in the last thirty days grouped by `source`, secrets, listings) for the Settings dialog; no table of its own. Its queries are tagged templates because Bun does not decode JSONB from parameterized `unsafe` queries. An additive startup migration runs inside a transaction and advisory lock, recording each applied entry in an `automator_migrations` ledger table so concurrent API starts serialize and never repeat work; no ORM is used. Imports `AuthUser`, `ProfileInput`, and `DatabaseStatus` types from `contracts`.
- **`packages/contracts`** — database-independent TypeBox schemas, inferred TypeScript types, endpoint paths, and HTTP response validation, with no dependency on Elysia, database drivers, or database schemas. A generic `EndpointContract` shape (method, path, params, body, per-status response schemas) is filled in and validated by shared `buildPath` and `parseResponse` helpers, and a common error schema and code union covers every endpoint's 400/401/403/404/409/422/500/503 responses. Flow shapes live in `flows.ts`: `FlowSummary` for lists, `FlowDocument` (versioned; nodes with one of the 37 catalog type ids, position, label and per-type `config`; edges with optional handle ids) for the builder, `FlowDocumentInput` (the document without its id, which the API mints) for create and save, `FlowRecord` (document plus timestamps) for reads, and the flow endpoint contracts. `findFlowDocumentProblem` adds the referential checks the schema cannot express: unique node and edge ids, and edges joining two existing, distinct nodes. `screens.ts` holds the four `screen.*` config schemas (`screenConfigSchemas`, every field with a default) and `parseScreenConfig`, which is lenient by design because rendering must not throw: it fills defaults, drops unknown keys, and replaces wrongly typed values. `marketplace.ts` holds the listing shapes (`MarketplaceListing` for cards, `MarketplaceListingDetail` with the flow snapshot, `PublishListingInput`), the marketplace endpoint contracts, `slugifyListingName`, and `listingNodeTypes`, which picks the distinct non-trigger node types a card highlights.
- **`packages/flow-engine`** — runs a `FlowDocument` in memory, importing only `contracts` so it can later run in the browser as well as the API. `runFlow` walks the graph from its unconnected trigger nodes (or, with `resume`, from an answered screen whose outputs are given, with `vars` seeded from the earlier run) in topological order, reporting each node result through `onNodeResult` as it lands: a node runs once every incoming edge has fired or gone dead, and only if at least one fired, so a condition node fires exactly one of its `true`/`false` handles and the other branch is skipped. Executors are a registry keyed by node type (`trigger`, `step`, or `screen`); a step reads its `config` through the contract schema with defaults filled and `{{input.handle}}`, `{{vars.name}}` and `{{trigger.path}}` templates resolved. Implemented today: every trigger type (handing its payload to its output handle), `logic.condition`, `logic.set-variable`, `logic.wait` (capped at 30 s), and `notify.discord` (POST to a `discord.com` webhook URL only). Screens stop the run as `waiting` because they need a visitor, unless the run's `screens` option is `auto`, in which case `autoAnswer` (`src/screens.ts`) answers them the way Simulate does: page and QR code continue on `next`, a confirmation takes the port its `simulate` config names (confirmed by default), and a form submits one value per field (its `sample` config, else a value for the type such as `visitor@example.com`); the node succeeds with that output plus a `simulated: { port }` key that is never a handle id, so nothing fires on it, and the outputs otherwise match what a real visitor produces; other types fail as not implemented; a failing node fails the run and every node not yet run is reported as skipped. The result is a `FlowRun` with one entry per document node.
- **`packages/miniapp`** — the visitor-facing side of a flow, shared by the runtime and the builder's preview; imports `contracts`, `ui` and `flow-engine`. The `MiniApp` component plays a document on the real engine in the browser: opening runs `runFlow` from the `trigger.miniapp-open` node (payload `{ openedAt }`) until the first `screen.*` node stops it as `waiting`; each visitor action resumes the run from that screen with the visitor's choice as the screen's output (`screenPorts` names the port; a form hands over its values keyed by field id, other actions `{ action: port }`), seeding `vars` from the previous run. While a run is in progress the interstitial lists the node results as `onNodeResult` reports them; a failed node ends in a "Something went wrong" screen naming it. The four screen types render from their `config` through `parseScreenConfig`. `encodeDocumentHash`/`decodeDocumentHash` carry a document in a URL fragment as base64url JSON. The apps register `node_modules/@automator/miniapp/src` as a Tailwind source.
- **`packages/api-client`** — shared server-only HTTP client built around one generic `request()` that sends any `EndpointContract` with a bearer header, a timeout, and contract validation. Its `./server` export provides `getHealth` and `requestAuth` (throwing `AuthApiError`) on top of `request()`, with callers supplying `API_URL`. The `server-only` marker prevents importing it into a Next.js client component.
- **`packages/ui`** — shared React primitives sourced from the Coss UI registry, built on Base UI: buttons, inputs, select, dialog, alert dialog, menu, tabs, tooltip, checkbox, switch, badge, field, textarea, separator, progress, and supporting components, plus `ThemeProvider` (next-themes) and a Coss-based `ThemeSelect`. An icon-only button requires an accessible name at the type level; a loading button stays keyboard-operable through `aria-disabled` rather than the native `disabled` attribute, and `Spinner` is decorative by default. Imported through explicit exports such as `@automator/ui/button`; supports Server and Client Components. No Next.js, API, or database dependency. `packages/ui/COSS.md` records provenance and local adaptations.
- **`packages/tailwind-config`** — shared Tailwind v4 stylesheet, Inter and Geist Mono fonts with real fallback stacks, and PostCSS configuration. Owns the neutral and chromatic color palettes, the semantic typography scale, and builder-canvas tokens (`canvas`, `node`, `edge`, `overlay`, `shadow-color`, `chart-1`..`chart-5`); `--accent` is a step distinct from `--popover`, and destructive text is split between the solid-fill foreground and a plain `--destructive-text`. `packages/ui/COSS.md` records the token rationale in full. Each frontend, including UI Lab, imports this stylesheet and `@automator/ui/styles.css`, which owns the z-index steps, and registers its own source directory; automatic class scanning is disabled.
- **`packages/typescript-config`** — strict base, React, and Next.js configurations.

## Boundary and contracts

The data access boundary is `web/runtime → api → db`. Neither frontend depends on `@automator/db`; both use server-side `API_URL` for backend access, and the API owns all database access. Define shared request/response shapes in `packages/contracts` and derive types from their schemas instead of duplicating interfaces. Elysia validates its responses against these schemas; Next.js validates unknown JSON against the same schema and HTTP status before consuming it. The API's root `onError` maps every failure to one of the shared error codes and never echoes internal messages; every response also carries `Cache-Control: no-store`, and requests are logged one line each when logging is enabled.

**Rate limits.** `apps/api/src/rate-limit.ts` keeps a sliding one-minute window per key in memory (one API instance) and the limited routes answer 429 `rate_limited` with a `Retry-After` header (whole seconds) once the window is full; refusals are not counted. The windows are per authenticated user for `POST /flows/run` and `POST /flows/:id/runs` together (30 calls a minute), every `/ai/*` route (10, applied at the plugin level so new AI routes inherit it), and `PUT /secrets/:name` (30); per client address for `POST /public/flows/:id/sessions` and its `answer` route together (60; the address is the first `X-Forwarded-For` entry, which Railway's proxy sets, else the socket address, else one shared bucket); and per flow for the webhook route (60). Reads and deletes are never limited. Each route factory takes `callsPerMinute` and `now`, which tests use; `createApp` takes `rateLimits`, which `index.ts` fills from `RATE_LIMIT_RUNS`, `RATE_LIMIT_AI`, `RATE_LIMIT_SECRETS`, `RATE_LIMIT_SESSIONS` and `RATE_LIMIT_WEBHOOKS` (positive integers; anything else keeps the default). The web app's same-origin proxies forward the status, and the builder shows "Too many requests. Try again in a moment." where it maps error codes.

## Auth

Dashboard authentication uses Privy (`@privy-io/react-auth` in web, `@privy-io/node` in API). `/login` is one custom Coss screen for email OTP, Google OAuth, and external Ethereum wallets, authenticating external wallets through SIWE. Every authenticated user gets an embedded Ethereum wallet, including users who signed in with an external wallet. `/onboarding` collects a display name and a unique username (3–24 lowercase letters, digits, or underscores, starting with a letter, uniqueness enforced in PostgreSQL); a fixed list of names is reserved.

The API verifies Privy token signatures, issuer, audience, and expiry through a scoped auth guard plugin shared by every route. With `PRIVY_VERIFICATION_KEY` configured, verification happens locally; without it, the SDK fetches JWKS, and any verification failure — including an outage — answers 401. `POST /auth/session` synchronizes the authenticated user and reads their embedded wallet from Privy, `GET /auth/me` reads the saved profile, and `PUT /auth/profile` saves only the caller's profile. The browser calls same-origin Next.js auth route handlers, which check the request's origin against its host — including a forwarded host behind Railway's proxy — before forwarding bearer tokens to the private API and mirroring the session into an HttpOnly `automator-session` cookie. A client `SessionProvider` is mounted in the `(auth)`, `(workspace)`, and `(canvas)` layouts rather than the root layout; the workspace and canvas ones seed it with the server-verified user so there is no loading flash, and it redirects to `/login`, clearing the session cookie first, when it detects a Privy sign-out. Privy owns authentication and refresh, and the cookie is a rendering mirror rather than a second authentication system.

## Flows

The API stores flows per user behind the same auth guard: `GET /flows` lists the caller's flows newest first, `POST /flows` creates one from a `FlowDocumentInput` and answers 201 with the record, `GET /flows/:id` reads one, and `PUT /flows/:id` replaces the document. A document that fails the input schema or the referential checks answers 422 `invalid_flow`; a flow the caller does not own answers 404, and a token whose user was never synchronized cannot create one. In the web app, Server Components call the API with the token from the session cookie through `apps/web/src/flows/server.ts`: `/create` builds the initial document (blank, or one of the seven curated examples: hand-authored `FlowDocument` fixtures in `apps/web/src/builder/examples.ts` with real node configs, positions and branch handles; the examples test runs each one with a scripted model and the engine's stub chain, and the only failure a fresh fork may show is a Discord node waiting for its own webhook) and creates it before redirecting to the canvas, `/flows` lists, and `/flows/[id]` loads the stored document or renders not-found. Saving from the canvas goes through the same-origin route handler `apps/web/src/app/api/flows/[id]`, which forwards the browser's Privy bearer token like the auth handlers do; the same handler's `DELETE` forwards to `DELETE /flows/:id`, which removes the flow with its listing and runs (both cascade in the database). `GET /public/flows/:id` (`apps/api/src/public/routes.ts`, no auth guard) returns the live record of a flow that has a marketplace listing, unredacted, so the runtime can host it; an unpublished or unknown id answers 404 either way.

## Flow runs

`POST /flows/run` runs any document the caller sends synchronously behind the auth guard and stores nothing (both run bodies accept `screens: "wait" | "auto"`, forwarded to the engine); the body is checked in the handler so an anonymous caller sees 401 before 400, and any signed-in user may run any document they send (a run's Discord webhook URL travels inside the node config). The canvas uses it while it has unsaved changes. `POST /flows/:id/runs` runs the caller's saved flow and stores the result in `automator_runs` (the finished `FlowRun`, a snapshot of the document it executed, the owner, status and timestamps; runs are deleted with their flow), answering 201 with a `FlowRunRecord` (run, current flow name, snapshot). `GET /flows/:id/runs` and `GET /runs` (optionally `?flowId=`) list `FlowRunSummary` rows newest first (the latter capped at 50 across every flow), and `GET /runs/:id` reads one record; all are owner-scoped. Every stored run carries a `source`: `manual` (Simulate), `webhook`, `schedule`, or `miniapp` (a visitor session). Whatever starts a stored run goes through `executeStoredRun` in `apps/api/src/runs/execute.ts`, which runs the record's document with the engine options the caller hands it (trigger, screens, mode-derived chain, secrets, sandbox, abort signal) and records the run under its owner with that source. In the web app `use-flow-run.ts` picks the persisted route whenever the store is clean, `/runs` lists through `listRuns` in `apps/web/src/flows/server.ts`, and `/flows/[id]?run=<id>` seeds the canvas's run store with a stored run. In the builder, Simulate serializes the canvas as it stands, posts it through the same-origin handlers under `apps/web/src/app/api/flows` (60 s timeout, to cover waits inside the flow) with the starting trigger's sample payload as the run's trigger payload: the config schemas of `trigger.manual`, `trigger.webhook`, `trigger.schedule` and `trigger.miniapp-open` carry a `samplePayload` field (JSON text, marked `contentMediaType: "application/json"`; the webhook default mirrors the hook route's `{ method, headers, query, body }`, the others default to `{}`), `parseSamplePayload` in `packages/contracts` reads it with `{}` as the fallback for a missing or unparsable value, and trigger executors never read their config, so the sample never appears in a real run's output; and keeps the answer in a per-builder run store next to the document store; each node card shows its status from the last run (`Ran`, `Failed` with the error text, `Skipped`, `Waiting`) until the next one starts. Stop aborts the browser request; the same-origin handler and the API forward the abort as `RunOptions.signal`, so the engine cancels at the next node and aborts the node in flight (the run finishes `failed` with "The run was cancelled."). Two constructs run in the engine itself: `logic.for-each` runs the nodes downstream of its `item` handle once per item as sequential sub-runs (capped by `maxItems`, at most 100; `vars` carry across; screens are not allowed inside) and then fires `done` with the items and per-pass results, and `logic.run-code` evaluates its function body through `RunOptions.sandbox`, which the API implements with QuickJS in WebAssembly (`apps/api/src/sandbox/quickjs.ts`: a fresh VM per node, no host bindings, JSON-only input and vars, 32 MB and 1 s) and the browser preview leaves absent, so the node fails there with a message that says so. `notify.telegram` (bot token and chat id) and `notify.email` (Resend key, sender, recipients, subject, text) join Discord as notification nodes; their credentials are `secret` config fields meant for `{{secrets.<name>}}`.

## Triggers

A saved flow runs on its own only while it is **active**: `automator_flows.enabled` (migration `0005_flow_triggers`, off by default) is toggled with `PATCH /flows/:id` `{ enabled }` and gates both trigger kinds below; mini-app sessions ignore it, since a published flow is meant to be opened. Each flow also gets a random `webhook_token` at creation, returned to its owner on every read as `webhookToken` and never in the public read.

**Webhook.** `POST /hooks/:flowId/:token` (`apps/api/src/hooks/routes.ts`) needs no session: it looks the flow up by id and token, refuses with 404 when the flow is missing, disabled, the token is wrong, or the document has no `trigger.webhook` node (all alike, so tokens cannot be probed), and answers 429 `rate_limited` beyond sixty calls per flow per minute (an in-memory window, per API instance). It then runs the flow from its first webhook trigger with `{ method, headers, query, body }` as the trigger payload (JSON bodies are parsed, anything else arrives as text), screens set to `wait`, onchain nodes live, and answers 202 with the stored run's id and status. Because the API has no public domain, the URL owners copy is on the web origin: `apps/web/src/app/api/hooks/[flowId]/[token]` forwards the request as-is (no session, no origin check, cookies and authorization stripped).

**Schedule.** `apps/api/src/scheduler.ts` runs inside the API process (started in `index.ts` when a database is configured, stopped on shutdown): every thirty seconds it lists the enabled flows, and for each one with a `trigger.schedule` node whose `every` parses (`30s`, `10m`, `1h`, `1d`, or bare minutes) it starts a run when the flow's newest `schedule` run is older than the shortest interval, with `{ at }` as the payload. A flow still running from the last tick is skipped, so runs never overlap, and a failing flow or store only logs. The clock and tick length are injectable for tests.

## Marketplace

A listing is a public snapshot of one of the caller's saved flows, so publishing never exposes later edits until the owner publishes again. Behind the auth guard, `GET /marketplace` lists every listing newest first, `GET /marketplace/:slug` returns one with its snapshot, `POST /marketplace` publishes the flow named in the body (the API mints a slug from the name, adding a numeric suffix when taken, and a second publish of the same flow updates the listing in place and keeps the slug), `DELETE /marketplace/:slug` removes the caller's listing, `POST /marketplace/:slug/fork` copies the snapshot into a new flow for the caller and answers 201 with the record, and `GET /flows/:id/listing` tells the builder whether a flow is listed. Input that fails the schema answers 422 `invalid_listing`; a user without a username (not onboarded) answers 403; a flow or listing the caller does not own answers 404. Before the snapshot is stored, `redactFlowSecrets` (contracts) resets every config field whose schema carries the `secret: true` marker (see `node-config.ts`: `secretFields`, `redactSecrets`), such as Discord webhook URLs, so a listing never carries the publisher's credentials and a fork shows those fields as "set your own"; the detail page carries the snapshot for a read-only graph preview; the live document behind `GET /public/flows/:id` is deliberately not redacted, since the mini-app runtime executes it. In the web app, Server Components read listings through `apps/web/src/marketplace/server.ts` and merge them with the curated examples, `/marketplace/[slug]/fork` forks through the API and redirects to the new canvas, and the builder's publish dialog calls the same-origin handlers under `apps/web/src/app/api/marketplace`, which forward the browser's Privy bearer token.

## Mini-apps

A flow that starts with `trigger.miniapp-open` is a mini-app: the visitor opens it and moves through its `screen.*` nodes (page, form, confirmation, QR code), each button choosing an output port, and the nodes wired between two screens run on `packages/flow-engine`; an unwired port ends the flow. A published flow runs on the API through sessions: `POST /public/flows/:id/sessions` runs it as the owner (with the owner's secrets and chain access) from the mini-app trigger to the first screen, stores the run in the owner's history with source `miniapp`, and answers a session id, a one-time token, and only the current screen (`nodeId`, type, label, its parsed config) plus the steps worked through; `POST /public/flows/:id/sessions/:sessionId/answer` takes `{ token, port, data? }`, resumes the run from that screen with the visitor's answer, stores that run too, and answers the next screen, `end`, or `failed`. A failed session never carries a node's error text (it can name URLs, addresses, revert data or secret names; the stored run keeps it for the owner's canvas and `/runs`): it answers `error` set to the one sentence `miniAppFailureMessage` ("This app hit a problem and could not continue."), a `code` the runtime can act on (`node_failed`, or `unconfigured`, `cancelled` and `timeout`, classified from the engine's error text in `failureCode`), and `help` when the flow owner filled the mini-app trigger's `visitorErrorMessage` config (for example how to reach them); the `steps` list names what ran and whether it failed, without errors. The document never leaves the API; sessions live in `automator_sessions` (token hash, waiting node, `vars`, opening payload, last run). A wrong token and an unknown session both answer 404; a session that already ended answers 409. Publishing is the owner's consent, so sessions run whether or not the flow's unattended triggers are enabled. The runtime renders a mini-app at `/a/[flowId]`, edge to edge on a phone and as a phone-sized card on wider viewports: the page reads the flow's public summary server-side (`GET /public/flows/:id` answers only id, name, description and update time), then the `RemoteMiniApp` component plays the session through the runtime's same-origin handlers under `/api/a/[flowId]/sessions`; a failed session renders `VisitorFailedView` inside the phone frame ("Something went wrong", the sentence, the owner's note, and a "Try again" button that starts a new session), and an API that cannot be reached or answers `rate_limited` renders the same view with its own sentence. When the flow is unpublished, or always with `?preview`, the document comes from the URL fragment that the builder's "Open in browser" link writes and plays in the browser on the in-browser engine (the owner's own preview of an unsaved canvas; `{{secrets.*}}` stay unresolved there). The web app's `NEXT_PUBLIC_RUNTIME_URL` names the runtime origin for that link. World App integration is deferred; the mini-app is a plain web page.

## Account

`GET /account/usage` (`packages/contracts/src/account.ts`, `apps/api/src/account/routes.ts`, behind the auth guard) answers the caller's `AccountUsage`: flow and active-flow counts, stored runs started in the last thirty days by source, secrets and listings, plus the window's start. The web app reads it through the same-origin proxy `apps/web/src/app/api/account/usage`, which forwards the browser's Privy bearer token like the other proxies, for the Settings dialog's Usage section.

## Secrets

Node config references credentials as `{{secrets.<name>}}` rather than holding them. Secrets are per user (`automator_secrets`: owner, name matching `^[a-z][a-z0-9_]{0,63}$`, ciphertext, timestamps) and encrypted in the API with AES-256-GCM under `SECRETS_KEY` (32 bytes, base64; required in production, generated per process with a warning in development) before the database sees them; a stored value is `v1.<iv>.<tag>.<ciphertext>`. `GET /secrets` lists names, `PUT /secrets/:name` creates or replaces a value, `DELETE /secrets/:name` removes one; no route returns a value. The engine resolves secrets per node through `RunOptions.secrets` (a `SecretsResolver` the API builds for the flow's owner from `createSecretsResolver`), reading only the names that node's config references; a referenced name the owner has not defined fails the node. Without a resolver, as in the builder's in-browser preview, the placeholder stays literal. Every server-side run path (`/flows/run`, `/flows/:id/runs`, webhook and schedule triggers, mini-app sessions) passes the owner's resolver. A `logic.set-variable` node that copies a secret into `vars` puts it into the run result, which the owner can read back.

## AI

AI runs over OpenRouter's OpenAI-compatible chat completions with plain `fetch`, behind one seam: `packages/flow-engine` defines `LanguageModel` (a chat request of messages, optional tools and a response format, answered with text and tool calls) and receives it through the executor context like `fetch`, so the engine stays browser-safe and tests script the model turn by turn with `scriptedModel`. `apps/api/src/ai/client.ts` implements the seam; `OPENROUTER_API_KEY` and `OPENROUTER_MODEL` (default `minimax/minimax-m3:free`, a free model that handles tools and JSON-schema answers; the Gemma free models were rate-limited and the Nemotron one failed structured answers when tested) are optional in every environment, and without a key the API passes no model: AI nodes then fail their run as unconfigured and the AI routes answer 503. Model failures are mapped to `unconfigured`, `timeout`, `upstream` or `invalid_response` and never echoed to clients.

Four node types run on it. `ai.generate-text` sends optional instructions plus a templated prompt and outputs `text`. `ai.classify` asks for one of the configured labels with a JSON-schema response format, rejects anything outside the set, and outputs `label` plus a handle named after the label. `ai.extract` takes a JSON schema as text, asks for a matching object, and checks the answer against a small in-engine matcher (type, enum, const, properties/required, items) before outputting `data`. `ai.agent` is a constrained tool loop: the config names the tools it may use from a fixed allowlist (`http_get` to configured hosts over https, `set_variable`, `discord_message` to the configured webhook), the model only ever sees those tools, `maxSteps` caps the turns, a disallowed tool or host is answered to the model as an error rather than executed, and every call is recorded in the node's `steps` output so a run can be audited and a test can assert the exact sequence.

`POST /ai/flows` (contract in `packages/contracts/src/ai.ts`) designs a flow from a prompt or, given the current document, edits it. The model is told the usable node types, their handle ids (`packages/contracts/src/flow-ports.ts`, which the web catalog mirrors under test) and config fields, and answers nodes and edges without positions; the API lays the graph out left to right by depth, cleans configs through their schemas, and validates the result against the document schema, the referential checks, the type allowlist (types with an executor or a screen), handle ids, single edges per input, a trigger, no orphans and no cycles. An invalid answer is sent back once with the problem; a second failure answers 422 `invalid_flow`. Secrets such as webhook URLs are left blank for the user to fill in.

## Onchain

Chain access sits behind one seam like the language model: `packages/flow-engine` defines `ChainProvider` (chain id and name, a `reader` for calls, an optional `account` and `signer` for the user's wallet, a `mode`, and the chain's USDC address), injected per run through `RunOptions.chain` and exposed on the executor context. viem is a dependency of the engine for ABI parsing, argument coercion and unit maths, but no transport: the API builds the provider from `CHAIN_ID` (default 84532, Base Sepolia), `CHAIN_RPC_URL` (default `https://sepolia.base.org`) and `USDC_ADDRESS` (default Circle's Base Sepolia USDC), all optional. Pointing `CHAIN_RPC_URL` at a local `anvil --fork-url` makes live runs hit the fork with no code change; Foundry is not required for anything else.

Writes run in one of two modes. `dry-run`, the default for Simulate, simulates the call as the user's wallet (`eth_call` plus a gas estimate) and answers `{ simulated: true, result, gas }` without broadcasting; reverts are decoded into the node error (`Reverted: NotOwner(0x…)`). `live`, which Simulate enables with its "Send real transactions" toggle and which trigger-driven runs always use, sends the transaction, waits for the receipt, and answers `{ hash, status, blockNumber, gasUsed, result }`; a reverted receipt fails the node. Reads never need a signer.

Signing uses Privy signers on the user's embedded wallet, the only option that serves both Simulate and unattended runs. One-time setup: an authorization key created in the Privy dashboard (Wallet infrastructure → Authorization keys), whose private key becomes `PRIVY_AUTHORIZATION_KEY` on the API and whose key quorum id becomes `NEXT_PUBLIC_PRIVY_SIGNER_ID` on the web app. Each user grants the signer once from the builder ("Enable server signing", `useSigners().addSigners`), after which the API signs through `createViemAccount` from `@privy-io/node` with a viem wallet client and no browser present. A run whose wallet lacks the grant, or an API without the key, fails the writing node with a message that says which of the two is missing; reads and dry-run simulations work with no Privy key at all.

Node types: `onchain.read-contract` and `onchain.write-contract` take an address, an ABI (JSON, or human-readable signatures one per line), a function name and a JSON array of arguments with templates, plus a native `value` for writes; integers in arguments may be strings. `onchain.transfer-token` sends the native coin or an ERC-20 (decimals read from the token). `onchain.sign-message` and `privy.sign-transaction` sign without broadcasting. `privy.wallet` outputs the user's address and chain id. `usdc.payment` and `usdc.payout` transfer the configured USDC (six decimals) and `usdc.balance` reads a balance, the user's own by default. Every output is JSON-safe: bigints travel as decimal strings.

## Environments and configuration

Development and production share one Railway PostgreSQL database; local development uses its public TCP endpoint with TLS, and the API uses the private connection URL. Copy each app's `.env.example` to `apps/api/.env`, `apps/web/.env.local`, and `apps/runtime/.env.local`. Privy configuration is split: web receives only `NEXT_PUBLIC_PRIVY_APP_ID`; the API receives `PRIVY_APP_ID`, `PRIVY_APP_SECRET`, and an optional `PRIVY_VERIFICATION_KEY` for local token verification, required in production. Local values live in ignored environment files; Railway production variables are configured directly on their respective services. No secret belongs in frontend code or checked-in infrastructure configuration.

API `/health` returns 200 when the database query succeeds and 503 when the database is unavailable or unconfigured. API `/health/live` and both frontends' `/health` only check their own process.

## Deploy (Railway)

Railway's `automator` project contains `web`, `api`, `runtime`, and `Postgres` in the `production` environment. `.railway/railway.ts` defines service commands, variables, networking, readiness checks, restart policies, and each service's build watch patterns, scoped to the packages it imports. The `web` and `runtime` services are public; `api` is only reachable over Railway's private network. All three build from the repository root with a Turbo package filter.

The connected application source is `ardasarico/automator` on GitHub, branch `main`. Deploy applications through GitHub pushes; do not upload local application files with `railway up`. Changes to `.railway/railway.ts` require a separate config plan/apply: use Railway CLI 5.49.2 or newer, run `railway config plan` to review changes, then `railway config apply`. Database credentials are kept in Railway, referenced by the API configuration.

## Tooling and verification

Root scripts delegate to Turborepo for development, builds, production startup, type checking, and tests. Build outputs are `.next/` for each frontend and `dist/` for the API. Development and production servers are persistent, uncached tasks. Workspace dependencies propagate build/typecheck cache invalidation, and a transit task propagates lint invalidation through shared configuration packages.

Run `bun install` and `bun run dev` from the repository root to start web (3000), API (3001), runtime (3002), and UI Lab (3003); filter to one app with `bun run dev --filter=@automator/web`. Use `bun run lint`, `bun run typecheck`, `bun run test`, `bun run build`, and `bun run format:check` for verification; lint and build must pass before push or deployment.

Oxlint runs React, Next.js, and accessibility rules for all three frontends and shared UI. Imports of the database package and configured database drivers, plus direct `process.env.DATABASE_URL` access, are lint errors in both frontends, UI, API client, and contracts. Oxfmt formats repository sources and configuration; READMEs, licenses, installed skills, and generated files are excluded.
