# Automator Architecture

Bun workspaces with Turborepo. Application code is TypeScript with strict checking. Each application owns its dependencies, TypeScript configuration, and scripts; shared packages export source directly and Next.js compiles the consumed TypeScript packages.

## Workspaces

- **`apps/web`** — Next.js App Router app, port 3000, the dashboard/builder host (workspace shell, flows, marketplace). Depends on `api-client`, `contracts`, `ui`, `miniapp`, plus `@xyflow/react` (React Flow) and `zustand` for the flow builder under `src/builder/`. Screen-level UI behaviour lives in `docs/web-ui.md`.
- **`apps/runtime`** — Next.js App Router app, port 3002, the host for shared end-user apps: `/a/[flowId]` plays a flow as its mini-app (see Mini-apps below), plus a landing page that explains what a mini-app link is, error/not-found screens, and a process health endpoint. Depends on `api-client`, `contracts`, `ui`, `miniapp`. Production uses `PORT` when set, otherwise 3002.
- **`apps/ui-lab`** — local Next.js component preview, port 3003. An app-owned sidebar and header surround previews of the installed UI primitives, with a theme toggle and content width presets. Agentation provides dev-only browser annotations without an Agent Sync server. Depends on `ui` only; no API or database dependency, no Railway service.
- **`apps/landing`** — Next.js marketing site, port 3004, deployed on its own Railway service and its own host. Depends on `ui` and `tailwind-config` only, with `ogl` for the vendored WebThreads hero shader (shared with the workspace home) and `next-themes` for theming; its illustrations are CSS keyframes. No API, database or contracts dependency; the prompt box hands off to the workspace through `NEXT_PUBLIC_APP_URL`.
- **`apps/api`** — Elysia app on Bun, port 3001 (overridable with `PORT`), listening on IPv6 for Railway private networking. `src/config.ts` reads the environment once at startup; production refuses to start when a required variable is missing, while development warns and continues. Depends on `contracts`, `db`, `flow-engine`.
- **`packages/db`** — Bun SQL connection pool and database health query (`SELECT 1`), timing out after three seconds. The `automator_users` table stores the Privy user ID, profile name, unique lowercase username, and verified embedded EVM wallet address; syncing a user preserves an existing wallet address when Privy reports none. The `automator_flows` table stores each flow's owner (a user, deleted with them), name and description as columns for listing, the graph (`version`, `nodes`, `edges`) as one JSONB document, and created/updated timestamps; the flow store's reads and writes are all scoped to the owner, so another user's flow behaves like a missing one; `findPublished` is the one exception, reading any flow whose `app_published` flag is set for the public read, alongside `findForWebhook` (id and token, enabled only) and `listEnabled` (every owner) for the trigger paths; `setEnabled` toggles activation and `setAppPublished` toggles mini-app sharing. The `automator_runs` table (`runs.ts`) keeps one immutable row per stored run: owner, flow (cascade), status, the executed document snapshot and the `FlowRun` result as JSONB, the `source` that started it, and start/finish timestamps, indexed per owner and per flow by start time; `latestStartedAt` serves the scheduler. The `automator_listings` table holds marketplace listings: a unique slug, the source flow (one listing per flow, deleted with it), the owner, name, a description of at most 280 characters, a JSONB snapshot of the graph, the highlighted node types, a fork count, and publish/update timestamps; the listing store reads join the owner for the byline, its writes are owner-scoped, and forking inserts the snapshot as a new flow and counts it in one transaction. The `automator_node_presets` table (`node-presets.ts`, migration `0016_node_presets`) keeps an owner's saved nodes: a name, the node type, its label and its config as JSONB, capped at 50 per owner under the owner row lock, deleted with the user. The `automator_event_cursors` table (`event-cursors.ts`, migration `0007_event_cursors`) keeps, per flow and onchain-event trigger node, the chain id and the last block whose logs were handled (a BIGINT that travels as text), deleted with the flow. The `automator_watch_state` table (`watch-state.ts`, migration `0010_watch_state`) keeps, per flow and watch trigger node, whether the comparison held at the last poll and the reading that produced it, deleted with the flow. The `automator_flow_versions` table (`flow-versions.ts`, migration `0009_flow_versions`) keeps a flow's save history: per flow a running `number` (unique with the flow), the name, description and graph as saved, and a timestamp, deleted with the flow; `record` assigns the next number in one statement scoped to the owner and prunes past the newest 50, `list` and `find` are owner-scoped. `account.ts` reads per-owner counts across these tables (flows and enabled flows, runs started in the last thirty days grouped by `source`, secrets, listings) for the Settings page; no table of its own. The rest of the schema is described where its feature is: `automator_secrets` and `automator_sessions` (migration `0006_secrets_sessions`, see Secrets and Mini-apps), `automator_api_keys` (`0017_api_keys`, see Auth), `automator_payments` (`0018_payments`, see Mini-apps), `automator_payment_policies` and `automator_payment_reservations` (`0013_payment_policies`, see Onchain), `automator_data_tables` and `automator_data_records` (`0014_data_tables`, see Data tables) and `automator_trigger_claims` (`0012_durable_trigger_claims`, see Triggers) — nineteen migrations building eighteen tables in all. Its queries are tagged templates because Bun does not decode JSONB from parameterized `unsafe` queries. An additive startup migration runs inside a transaction and advisory lock, recording each applied entry in an `automator_migrations` ledger table so concurrent API starts serialize and never repeat work; no ORM is used. Imports `AuthUser`, `ProfileInput`, and `DatabaseStatus` types from `contracts`.
- **`packages/contracts`** — database-independent TypeBox schemas, inferred TypeScript types, endpoint paths, and HTTP response validation, with no dependency on Elysia, database drivers, or database schemas. A generic `EndpointContract` shape (method, path, params, body, per-status response schemas) is filled in and validated by shared `buildPath` and `parseResponse` helpers, and a common error schema and code union covers every endpoint's 400/401/403/404/409/422/429/500/503 responses. Flow shapes live in `flows.ts`: `FlowSummary` for lists, `FlowDocument` (versioned; an optional `chainId` from the registry in `chains.ts`, read through `flowChainId`, which answers Base Sepolia for older documents; nodes with one of the 46 catalog type ids, position, label and per-type `config`; edges with optional handle ids) for the builder, `FlowDocumentInput` (the document without its id, which the API mints) for create and save, `FlowRecord` (document plus timestamps) for reads, and the flow endpoint contracts. A document may also carry `groups`, the labelled frames the builder draws around nodes (`FlowGroup`: label, position, size), with a node's `parentId` naming its frame; node positions stay absolute in the document so the engine, the AI, the miniature and the database never have to know a group exists, and only the builder converts to the relative positions React Flow wants. `findFlowDocumentProblem` adds the referential checks the schema cannot express: unique node, edge and group ids, edges joining two existing, distinct nodes, and a `parentId` naming a group that exists. `screens.ts` holds the eight screen config schemas (`screenConfigSchemas`, every field with a default: the four `screen.*` types, the three identity screens `privy.login`, `world.id-verify` and `world.selfie-check` from `identity.ts`, and `usdc.payment` from `onchain-configs.ts`) and `parseScreenConfig`, which is lenient by design because rendering must not throw: it fills defaults, drops unknown keys, and replaces wrongly typed values. `identity.ts` also holds what those screens produce (`VisitorUser`, `WorldVerification`, `WorldRejection`, and for the selfie check `WorldSelfieCheck` and `WorldSelfieRejection`, both carrying a `verified` boolean), the credential list `worldCredentials` (`device`, `orb`, `selfie`), the IDKit result shape the runtime sends back (`WorldProof`) and the signed request context the API sends out (`WorldRequest`), plus the sample answers Simulate and the preview use. `marketplace.ts` holds the listing shapes (`MarketplaceListing` for cards, `MarketplaceListingDetail` with the flow snapshot, `PublishListingInput`), the marketplace endpoint contracts, `slugifyListingName`, and `listingNodeTypes`, which picks up to four distinct non-trigger node types a card highlights. A listing also carries the `FlowOutline` its snapshot draws (`documentOutline` in `flows.ts`, node ids, types and positions with the edges between them), so a list draws each flow's own shape without asking for the document.
- **`packages/flow-engine`** — runs a `FlowDocument` in memory, importing only `contracts` so it can later run in the browser as well as the API. `runFlow` walks the graph from its unconnected trigger nodes (or, with `resume`, from an answered screen whose outputs are given, with `vars` and completed node outputs seeded from the earlier run) in topological order, reporting each node result through `onNodeResult` as it lands: a node runs once every incoming edge has fired or gone dead, and only if at least one fired, so a condition node fires exactly one of its `true`/`false` handles and the other branch is skipped. Executors are a registry keyed by node type (`trigger`, `step`, or `screen`); a step reads its `config` through the contract schema with defaults filled and `{{input.handle}}`, `{{vars.name}}` and `{{trigger.path}}` templates resolved. Every catalogue type has an executor: the trigger types (handing their payload to their output handle), the logic nodes (condition, switch, filter, merge, set-variable, wait capped at 30 s, run-code; `logic.for-each` is the one the engine runs itself, see Flow runs), the AI nodes, the onchain, Privy and USDC nodes, the Discord, Telegram and email notifications, and the screens. Screens stop the run as `waiting` because they need a visitor, unless the run's `screens` option is `auto`, in which case `autoAnswer` (`src/screens.ts`) answers them the way Simulate does: page and QR code continue on `next`, a confirmation takes the port its `simulate` config names (confirmed by default), a form submits one value per field (its `sample` config, else a value for the type such as `visitor@example.com`), a Privy login signs in as the `simulate` visitor of its config, which the engine also keeps as `vars.visitor` so `{{vars.visitor.wallet}}` reads the same in Simulate as in a hosted session, and a World ID check or Selfie Check takes `verified` with a sample nullifier (or `rejected`, when its `simulate` says so); the node succeeds with that output plus a `simulated: { port }` key that is never a handle id, so nothing fires on it, and the outputs otherwise match what a real visitor produces; a failing node fails the run and every node not yet run is reported as skipped. `resume` may carry an `error` instead of outputs, in which case the answered screen itself is recorded as failed (how the API reports an identity screen it cannot verify). The result is a `FlowRun` with one entry per document node.
- **`packages/miniapp`** — the visitor-facing side of a flow, shared by the runtime and the builder's preview; imports `contracts`, `ui` and `flow-engine`. The `MiniApp` component plays a document on the real engine in the browser: opening runs `runFlow` from the `trigger.miniapp-open` node (payload `{ openedAt }`) until the first `screen.*` node stops it as `waiting`; each visitor action resumes the run from that screen with the visitor's choice as the screen's output (`screenPorts` names the port; a form hands over its values keyed by field id, other actions `{ action: port }`), seeding `vars` from the previous run. While a run is in progress the interstitial lists the node results as `onNodeResult` reports them; a failed node ends in a "Something went wrong" screen naming it. The four screen types render from their `config` through `parseScreenConfig`. The three identity screens (`identity.tsx`) render a title, message and one button, and act through an `IdentityActions` context the host provides (`privyLogin`, `worldVerify`, `worldSelfieCheck`, `inWorldApp`); without one, as in the builder's preview and the in-browser engine, the button plays the screen's sample answer and the screen says so. The current preview handoff passes a captured document directly between the builder and its opened runtime window with origin, window, nonce and flow identity checks; only a random nonce enters the URL. The apps register `node_modules/@automator/miniapp/src` as a Tailwind source.
- **`packages/api-client`** — shared server-only HTTP client built around one generic `request()` that sends any `EndpointContract` with a bearer header, a timeout, and contract validation. Its `./server` export provides `getHealth` and `requestAuth` (throwing `AuthApiError`) on top of `request()`, with callers supplying `API_URL`. The `server-only` marker prevents importing it into a Next.js client component.
- **`packages/ui`** — shared React primitives sourced from the Coss UI registry, built on Base UI: buttons, inputs, select, dialog, alert dialog, menu, tabs, tooltip, checkbox, switch, badge, field, textarea, separator, progress, and supporting components, plus `ThemeProvider` (next-themes) and a Coss-based `ThemeSelect`. An icon-only button requires an accessible name at the type level; a loading button stays keyboard-operable through `aria-disabled` rather than the native `disabled` attribute, and `Spinner` is decorative by default. Imported through explicit exports such as `@automator/ui/button`; supports Server and Client Components. No Next.js, API, or database dependency. `packages/ui/COSS.md` records provenance and local adaptations.
- **`packages/tailwind-config`** — shared Tailwind v4 stylesheet, Inter and Geist Mono fonts with real fallback stacks, and PostCSS configuration. Owns the neutral and chromatic color palettes, the semantic typography scale, and builder-canvas tokens (`canvas`, `node`, `edge`, `overlay`, `shadow-color`, `chart-1`..`chart-5`); `--accent` is a step distinct from `--popover`, and destructive text is split between the solid-fill foreground and a plain `--destructive-text`. `packages/ui/COSS.md` records the token rationale in full. Each frontend, including UI Lab, imports this stylesheet and `@automator/ui/styles.css`, which owns the z-index steps, and registers its own source directory; automatic class scanning is disabled.
- **`packages/typescript-config`** — strict base, React, and Next.js configurations.

## Boundary and contracts

The data access boundary is `web/runtime → api → db`. Neither frontend depends on `@automator/db`; both use server-side `API_URL` for backend access, and the API owns all database access. Define shared request/response shapes in `packages/contracts` and derive types from their schemas instead of duplicating interfaces. Elysia validates its responses against these schemas; Next.js validates unknown JSON against the same schema and HTTP status before consuming it. The API's root `onError` maps every failure to one of the shared error codes and never echoes internal messages; every response also carries `Cache-Control: no-store`, and requests are logged one line each when logging is enabled.

**Rate limits.** `apps/api/src/rate-limit.ts` keeps a sliding one-minute window per key in memory (one API instance) and the limited routes answer 429 `rate_limited` with a `Retry-After` header (whole seconds) once the window is full; refusals are not counted. The windows are per authenticated user for `POST /flows/run` and `POST /flows/:id/runs` together (30 calls a minute), the AI turn route `POST /flows/:id/ai/messages` (10, checked once the flow's ownership has resolved so a mistyped or foreign id costs nothing; reading, patching and clearing a conversation are never limited), and `PUT /secrets/:name` (30); per client address for `POST /public/flows/:id/sessions` and its `answer` route together (60; the address is the first `X-Forwarded-For` entry, which the runtime's session handlers copy from the visitor's request (Railway's proxy sets it there; the API itself only ever sees the runtime), else the socket address, else one shared bucket); and per flow for the webhook route (60). Reads and deletes are never limited. Data writes are limited per user too (`/data/*`, 30). Each route factory takes `callsPerMinute` and `now`, which tests use; `createApp` takes `rateLimits`, which `config.ts` fills from `RATE_LIMIT_RUNS`, `RATE_LIMIT_DATA`, `RATE_LIMIT_AI`, `RATE_LIMIT_SECRETS`, `RATE_LIMIT_SESSIONS`, `RATE_LIMIT_WEBHOOKS` and `RATE_LIMIT_API` (positive integers; anything else keeps the default). The web app's same-origin proxies forward the status, and the builder shows "Too many requests. Try again in a moment." where it maps error codes.

## Auth

Dashboard authentication uses Privy (`@privy-io/react-auth` in web, `@privy-io/node` in API). `/login` is one custom Coss screen for email OTP, Google OAuth, and external Ethereum wallets, authenticating external wallets through SIWE. Every authenticated user gets an embedded Ethereum wallet, including users who signed in with an external wallet. `/onboarding` collects a display name and a unique username (3–24 lowercase letters, digits, or underscores, starting with a letter, uniqueness enforced in PostgreSQL); a fixed list of names is reserved.

The API verifies Privy token signatures, issuer, audience, and expiry through a scoped auth guard plugin shared by every route. With `PRIVY_VERIFICATION_KEY` configured, verification happens locally; without it, the SDK fetches JWKS, and any verification failure — including an outage — answers 401. `POST /auth/session` synchronizes the authenticated user and reads their embedded wallet from Privy, `GET /auth/me` reads the saved profile, and `PUT /auth/profile` saves only the caller's profile. The browser calls same-origin Next.js auth route handlers, which check the request's origin against its host — including a forwarded host behind Railway's proxy — before forwarding bearer tokens to the private API and mirroring the session into an HttpOnly `automator-session` cookie. A client `SessionProvider` is mounted in the `(auth)`, `(workspace)`, and `(canvas)` layouts rather than the root layout; the workspace and canvas ones seed it with the server-verified user so there is no loading flash, and it redirects to `/login`, clearing the session cookie first, when it detects a Privy sign-out. Privy owns authentication and refresh, and the cookie is a rendering mirror rather than a second authentication system.

Machines authenticate with an **API key** instead of a session. `POST /api-keys` mints one (`apps/api/src/api-publishing/key-routes.ts`, behind the same Privy guard): `ak_` plus 32 random bytes in base64url, of which only a SHA-256 hash and the first 11 characters reach `automator_api_keys` (migration `0017_api_keys`), so the plaintext exists once, in the 201 answer. `GET /api-keys` lists names, visible heads and last use; `DELETE /api-keys/:id` revokes one; an owner holds at most 20 live keys (a 21st answers 409). The machine guard (`api-publishing/guard.ts`) accepts only a bearer token starting `ak_`, resolves it through `createApiKeyVerifier` (`verify.ts`, which hashes the key, looks it up, and stamps `last_used_at` at most once a minute, never on the request's critical path) and hands the route a `caller` rather than `claims`. A Privy token is refused on the `/v1` routes and an API key is refused on the dashboard routes, so neither credential can be replayed as the other, and a key reaches only its owner's published flows, never their account.

Mini-app visitors are a separate case: a `privy.login` screen signs the visitor in with the same Privy app inside the runtime (`apps/runtime/src/app/a/[flowId]/identity-host.tsx`, `@privy-io/react-auth` with the screen's allowed methods and an embedded wallet created on first sign-in), and the visitor's access token travels once in the session answer. The API verifies it like a dashboard token (`IdentityProvider.visitor`), looks the user up and derives `{ userId, wallet, email, loginMethod }` itself (`describeVisitor`: the embedded wallet else the first Ethereum wallet, the email else the Google address, and the login method of the account verified most recently), so a visitor cannot claim another identity; nothing about the visitor is stored beyond the run's outputs and `vars.visitor`. A rejected token answers 401 and leaves the session on the screen; the runtime shows the login screen again with the note "Your sign-in could not be verified. Try again." (`stateAfterFailure` in `packages/miniapp/src/remote-mini-app.tsx`).

## Flows

The API stores flows per user behind the same auth guard: `GET /flows` lists the caller's flows newest first, `POST /flows` creates one from a `FlowDocumentInput` and answers 201 with the record, `GET /flows/:id` reads one, and `PUT /flows/:id` replaces the document. A document that fails the input schema or the referential checks answers 422 `invalid_flow`; a flow the caller does not own answers 404, and a token whose user was never synchronized cannot create one. Every create records version 1 of the flow and every `PUT` whose graph (`version`, `chainId`, `nodes`, `edges`) differs from the stored one records the next version (`apps/api/src/flows/versions.ts`; a rename alone records nothing); `GET /flows/:id/versions` lists them newest first as `FlowVersionSummary` (number, name, time, node count) and `GET /flows/:id/versions/:number` answers the `FlowVersionRecord` with its document, 404 for another owner's flow or an unknown number. Reads that return a stored document (`GET /flows/:id`, `GET /marketplace/:slug`, `GET /runs/:id`, and the saved-flow run) check it against `flowDocumentSchema` first (`apps/api/src/flows/stored.ts`) and answer 422 `invalid_flow` with a log line naming the flow when it no longer matches, so a document saved before a node type was retired never becomes a 500 from the response validator; retiring a type comes with a migration that rewrites stored documents (`0008_retire_selfie_check` turned `world.selfie-check` nodes into `world.id-verify` in flows, listing snapshots, listing node types and run snapshots, keeping configs and edges). In the web app, Server Components call the API with the token from the session cookie through `apps/web/src/flows/server.ts`: `/create` builds the initial document (blank, or one of the thirteen curated examples: hand-authored `FlowDocument` fixtures in `apps/web/src/builder/examples.ts` with real node configs, positions, branch handles and sample form values; the examples test runs each one with a scripted model and the engine's stub chain, and the only failure a fresh fork may show is a Discord node waiting for its own webhook) and creates it before redirecting to the canvas, `/flows` lists, and `/flows/[id]` loads the stored document or renders not-found. Saving from the canvas goes through the same-origin route handler `apps/web/src/app/api/flows/[id]`, which forwards the browser's Privy bearer token like the auth handlers do; the same handler's `DELETE` forwards to `DELETE /flows/:id`, which removes the flow with its listing and runs (both cascade in the database). `GET /public/flows/:id` (`apps/api/src/public/routes.ts`, no auth guard) returns the public summary (id, name, description, update time) of a flow published as a mini app, so the runtime can host it as a session (see Mini-apps); the document never leaves the API, and an unpublished or unknown id answers 404 either way.

## Flow runs

`POST /flows/run` runs any document the caller sends synchronously behind the auth guard and stores nothing (both run bodies accept `screens: "wait" | "auto"`, forwarded to the engine); the body is checked in the handler so an anonymous caller sees 401 before 400, and any signed-in user may run any document they send (a run's Discord webhook URL travels inside the node config). The canvas uses it while it has unsaved changes. `POST /flows/:id/runs` runs the caller's saved flow and stores the result in `automator_runs` (the finished `FlowRun`, a snapshot of the document it executed, the owner, status and timestamps; runs are deleted with their flow), answering 201 with a `FlowRunRecord` (run, current flow name, snapshot). `GET /flows/:id/runs` and `GET /runs` (optionally `?flowId=`) list `FlowRunSummary` rows newest first in keyset pages: `?limit=` (25 by default, at most 100, a decimal string) and `?cursor=` (opaque, minted by `packages/db` from the last row's start time and id) select the page and the answer carries `nextCursor` while older runs remain; an unreadable cursor or limit answers 400. `GET /runs/:id` reads one record, and `GET /runs/stats` (optionally `?flowId=`) counts the caller's runs by UTC day and outcome over the last `runStatsWindowDays` (14) days for the band above `/runs`; all are owner-scoped. Every stored run carries a `source`: `manual` (Simulate), `webhook`, `schedule`, `event` (the onchain-event listener), `watch` (a price or balance crossing), `miniapp` (a visitor session), or `api` (a machine call; migration `0019_run_source_api` widened the table's own check to match `flowRunSourceSchema`, and a db integration test stores every value the contract names so the two cannot drift again). A run may also carry a run-level `output`: `logic.return` resolves its `{ name, value }` templates and the engine records the first Return the run reaches as `FlowRun.output` — replayed answers and loop bodies included — while the same object travels on the node's own `output` port, so a Return in the middle of a flow does not end it. `/runs/[id]` shows it as an Answer section and the builder's run panel as “Answered the caller”. Whatever starts a stored run goes through `executeStoredRun` in `apps/api/src/runs/execute.ts`, which runs the record's document with the engine options the caller hands it (trigger, screens, mode-derived chain, secrets, sandbox, abort signal) and records the run under its owner with that source. In the web app `use-flow-run.ts` picks the persisted route whenever the store is clean, `/runs` lists through `listRuns` in `apps/web/src/flows/server.ts` (a "Load older runs" link carries `?cursor=`), `/runs/[id]` renders one stored record in full through `getRun`, and `/flows/[id]?run=<id>` seeds the canvas's run store with a stored run. In the builder, Simulate serializes the canvas as it stands, posts it through the same-origin handlers under `apps/web/src/app/api/flows` (60 s timeout, to cover waits inside the flow) with the starting trigger's sample payload as the run's trigger payload: the config schemas of `trigger.manual`, `trigger.webhook`, `trigger.schedule` and `trigger.miniapp-open` carry a `samplePayload` field (JSON text, marked `contentMediaType: "application/json"`; the webhook default mirrors the hook route's `{ method, headers, query, body }`, the others default to `{}`), `parseSamplePayload` in `packages/contracts` reads it with `{}` as the fallback for a missing or unparsable value, and trigger executors never read their config, so the sample never appears in a real run's output; and keeps the answer in a per-builder run store next to the document store; each node card shows its status from the last run (`Ran`, `Failed` with the error text, `Skipped`, `Waiting`) until the next one starts. Stop aborts the browser request; the same-origin handler and the API forward the abort as `RunOptions.signal`, so the engine cancels at the next node and aborts the node in flight (the run finishes `failed` with "The run was cancelled."). Two constructs run in the engine itself: `logic.for-each` runs the nodes downstream of its `item` handle once per item as sequential sub-runs (capped by `maxItems`, at most 100; `vars` carry across; screens are not allowed inside) and then fires `done` with the items and per-pass results, and `logic.run-code` evaluates its function body through `RunOptions.sandbox`, which the API implements with QuickJS in WebAssembly (`apps/api/src/sandbox/quickjs.ts`: a fresh VM per node, no host bindings, JSON-only input and vars, 32 MB and 1 s) and the browser preview leaves absent, so the node fails there with a message that says so. `notify.telegram` (bot token and chat id) and `notify.email` (Resend key, sender, recipients, subject, text) join Discord as notification nodes; their credentials are `secret` config fields meant for `{{secrets.<name>}}`.

## Triggers

A saved flow runs on its own only while it is **active**: `automator_flows.enabled` (migration `0005_flow_triggers`, off by default) is toggled with `PATCH /flows/:id` `{ enabled }` and gates the unattended trigger kinds below; mini-app sessions ignore it, since a published flow is meant to be opened. Sharing the flow as a mini app is the separate `automator_flows.app_published` flag (migration `0015_flow_app_publishing`, off by default, backfilled for the flows that already had a listing), toggled with `PATCH /flows/:id` `{ appPublished }`; the patch body carries either field or both, and an empty one answers 422. The patch is where a broken flow is stopped: `{ enabled: true }` is refused with 422 `invalid_flow` and a `problems` list (`findActivationBlockers` on the stored document, errors only, so a direct API call cannot skip it), and when the API can sign at all (`chainFactory.canSign`) and the stored flow has signer nodes (`findSignerNodes` in `packages/contracts/src/flow-checks.ts`: the five types whose executor calls `requireSigner`, from `onchain.write-contract` to `usdc.payout`; a visitor's `usdc.payment` is not one of them), both `{ enabled: true }` and `{ appPublished: true }` are refused with one error per signer node (`findSigningBlockers`, "needs server signing, which is off for your wallet") while the owner's wallet does not carry the configured signer, read through the same Privy lookup `GET /wallet` reports as `signing`; a lookup that fails answers 503 rather than passing. Turning either flag off is never refused. The builder asks `GET /wallet` first (`useWalletSigning` in `apps/web/src/builder`): the Share dialog and the flow settings' Active switch name the nodes, hold the action, and show `EnableSigningButton` inline until the API confirms the signer, and a refusal's `problems` are listed in the dialog rather than a generic error. Publishing an app and listing the flow in the marketplace are independent choices: the builder's Share menu offers both, and an unlisted app link is unlisted, not access-controlled. Each flow also gets a random `webhook_token` at creation, returned to its owner on every read as `webhookToken` and never in the public read.

**API.** A flow that starts at `trigger.api` is callable over HTTP while it is active, the same switch webhooks use. The trigger's config declares a `description` and an `inputs` array of `{ name, type: text | number | boolean | address, description, required }`, and its `input` handle carries the validated object, so downstream nodes read `{{input.<handle>.<name>}}` the way they read a webhook's request. Everything derived from that declaration lives in `packages/contracts/src/api-publishing.ts` — `flowApiSchema` (name, description, inputs, and the names every `logic.return` answers with), `validateFlowApiInput` (coercing numeric and boolean strings, checking addresses, and reporting every wrong field at once) and `describeFlowApiProblems` (those problems as one sentence) — so the endpoint, the builder's curl example and any tool description are read off the same document. Two machine routes sit under `/v1`, each requiring an API key and rate-limited per owner (`RATE_LIMIT_API`, sixty a minute by default): `GET /v1/flows` lists the caller's active API flows with their schemas (`api-publishing/callable-flows.ts` over `FlowStore.listEnabledForOwner`), and `POST /v1/flows/:id/invoke` validates the JSON body against the declaration (422 with per-field `problems`), runs the flow synchronously through `executeStoredRun` with source `api` and `screens: "wait"`, and answers 200 `{ runId, status, output }`. A flow that is missing, off, another owner's, or without an API trigger is one flat 404; a run that stops at a screen is stored and answered 409 `waiting_on_screen`, which is why the flow checks warn about screens in an API flow. The handler is thin: `invokeApiFlow` (`api-publishing/invoke.ts`) returns `not_found`, `invalid_input`, `waiting_on_screen` or `ok` for it to map, so the MCP transport calls a published flow exactly as an HTTP caller does. There is no web proxy in front of `/v1`: machine callers reach the API host directly (`NEXT_PUBLIC_API_URL`), which keeps a synchronous run off the browser proxy's timeout.

**MCP.** The same callable flows reach an assistant as tools over the Model Context Protocol. `POST /mcp` (`apps/api/src/mcp/routes.ts`) is a stateless Streamable HTTP endpoint on `@modelcontextprotocol/sdk`'s `WebStandardStreamableHTTPServerTransport`, which speaks Web `Request`/`Response` and so needs no Node adapter under Elysia; a server and transport are built for the key's owner on each request and closed with it, so there is no session to keep and any instance answers any request, while `GET` and `DELETE` answer 405 rather than hold open a stream that would never send anything. It takes the same API key as `/v1` (through `readBearerApiKey`, so a Privy token is refused without a database read) and the same `RATE_LIMIT_API` bucket per owner. `tools/list` answers one tool per callable flow plus a fixed `list_flows`, which returns them all with their schemas so an assistant can discover in one call. `mcp/tools.ts` derives each tool from the flow's `FlowApiSummary`: the name is the flow's name slugged with six characters of its id appended, so two flows sharing a name stay apart; the description is the trigger's, or a generated sentence when the author wrote none; the `inputSchema` is JSON Schema over the declared inputs, with `address` narrowed to `^0x[0-9a-fA-F]{40}$` and `additionalProperties` false, so a misspelled argument fails rather than arriving as a missing one. `tools/call` runs the flow through `invokeApiFlow` (`mcp/source.ts` is the whole adapter), so a tool call and an HTTP call cannot disagree about what is callable or what invalid input means; a finished run answers its output as text, as `structuredContent` when it is an object, and its id and status in `_meta`. Every refusal is an `isError` result carrying one sentence a caller outside the account may read — the input problems through `describeFlowApiProblems`, that the flow is no longer published, or that it stops at a screen a tool call cannot answer — and an unexpected throw is replaced by a fixed sentence, since the SDK would otherwise copy its message, hosts and all, into the JSON-RPC error. The builder's Use as API dialog carries the server URL and copyable snippets for Claude Code and config-file clients (`apps/web/src/builder/mcp-section.tsx`).

**Webhook.** `POST /hooks/:flowId/:token` (`apps/api/src/hooks/routes.ts`) needs no session: it looks the flow up by id and token, refuses with 404 when the flow is missing, disabled, the token is wrong, or the document has no `trigger.webhook` node (all alike, so tokens cannot be probed), and answers 429 `rate_limited` beyond sixty calls per flow per minute (an in-memory window, per API instance). It then runs the flow from its first webhook trigger with `{ method, headers, query, body }` as the trigger payload (JSON bodies are parsed, anything else arrives as text), screens set to `wait`, onchain nodes live, and answers 202 with the stored run's id and status. The URL owners copy is on the web origin, which is where the flow settings dialog builds it from: `apps/web/src/app/api/hooks/[flowId]/[token]` forwards the request as-is (no session, no origin check, cookies and authorization stripped).

**Schedule.** `apps/api/src/scheduler.ts` runs inside the API process (started in `index.ts` when a database is configured, stopped on shutdown): every thirty seconds it lists enabled flows and considers each `trigger.schedule` node whose `every` parses (`30s`, `10m`, `1h`, `1d`, or bare minutes). A trigger becomes due when its latest schedule history or durable admission is older than its interval, with `{ at }` as the payload. Admission rechecks the interval under the flow-row lock after wallet preparation. In-process tracking prevents overlapping work in one scheduler; durable unresolved claims prevent overlapping polling-trigger executions across instances. Those claims live in `automator_trigger_claims`, one row per occurrence, unique on flow, node, polling revision, source and occurrence key. A claim is `running`, `completed` or `uncertain`, and both unfinished states block further admission for that flow, so an effect whose outcome could not be confirmed is never repeated rather than being retried. A failing flow or store only logs. The clock and tick length are injectable for tests.

**Onchain event.** The same scheduler tick polls the chain for every enabled flow with a `trigger.onchain-event` node (config in `packages/contracts/src/onchain-configs.ts`: the emitting `address`, the `event` as one human-readable ABI signature such as `Transfer(address indexed from, address indexed to, uint256 value)`, an optional `args` filter as a JSON object over the indexed inputs, and `samplePayload`, the payload Simulate hands the trigger). Per trigger node it reads the flow's chain through the chain factory's `EventReader` (`apps/api/src/chain/events.ts`, viem `getLogs` with the event's topics, indexed-argument topics and strict decoding) from the node's cursor to the head, at most 2000 blocks per tick so a flow far behind catches up over several ticks, and starts one stored run per log through `executeStoredRun` with source `event`, screens `wait`, the owner's secrets and a live chain, and `{ event, args, address, blockNumber, blockHash, transactionHash, logIndex, chainId }` as the payload (bigints as decimal strings). A fresh cursor, or one recorded on another chain after the flow moved, starts ten blocks behind the head, so there is no historical replay. The cursor lives in `automator_event_cursors`; an RPC failure logs and leaves it untouched for the next tick; an occurrence that could not start or is unresolved leaves it before that log's block. Completed occurrences have durable identities using chain, transaction hash and log index, so rereading after a cursor-write failure does not repeat their effects; and a trigger whose config cannot be read (blank address, unparsable signature, a filter naming a non-indexed argument) logs without touching the chain. Polling shares the scheduler's per-flow in-flight set; persistent flow-wide claims separately prevent concurrent effect execution by multiple scheduler instances. Because the scheduler runs inside the API process, a development API pointed at the shared database polls for that database's active flows too.

**Price and balance.** The same tick also polls the two watch triggers (`packages/contracts/src/watch-configs.ts`; the poller is `apps/api/src/watch/`). `trigger.price` reads a Chainlink aggregator on the flow's own chain through the chain factory's read-only `ChainReader` (`latestRoundData`, plus `decimals` only when the pair is `custom`): `pair` picks one of the addresses `chainlinkFeeds` publishes for that chain (nine on Base Sepolia, none on World Chain Sepolia), `custom` reads the `feed` address typed in. `trigger.balance` reads a wallet's ERC-20 or native balance from The Graph's Token API (`GET /v1/evm/balances`, bearer `TOKEN_API_KEY` from The Graph Market, origin overridable with `TOKEN_API_URL`; a REST product separate from the subgraph gateway the `graph.query-subgraph` node uses, see Subgraphs below); that API serves mainnets only (`mainnet`, `base`, `arbitrum-one`), so the watched network is independent of the chain the flow transacts on, and a token the wallet does not hold reads as zero rather than as a failure. Both compare the reading against a `threshold` with one of `below`, `at_or_below`, `above`, `at_or_above`. Readings and thresholds are compared as scaled bigints, never as floats (`watch/threshold.ts` parses a decimal string at the source's own `decimals`, truncating rather than rounding), so an 18-decimal balance keeps its precision. A run starts only on the crossing: `automator_watch_state` holds the last poll's verdict, a watcher whose condition is already true when the flow is enabled fires once on the first poll, and it re-arms only after the condition goes false again. After wallet preparation, the crossing and durable execution claim commit atomically under the flow-row lock. A failed run does not retry every tick; an unresolved run blocks further polling-trigger executions for the flow rather than risking duplicate effects. Runs are stored through `executeStoredRun` with source `watch`, screens `wait`, the owner's secrets and a live chain. A config the poller cannot read (a pair the chain does not publish with no `feed` given, an invalid address, an unreadable threshold) logs as "cannot watch" without a run; a provider failure logs as "watch failed" and retries next tick; a missing Token API key leaves balance watchers idle and says so. Both trigger types count as unattended triggers, so a flow carrying one can be activated like a scheduled or webhook flow.

**Subgraphs.** `graph.query-subgraph` (`packages/contracts/src/graph-configs.ts`; executor in `packages/flow-engine/src/graph-executors.ts`, client in `graph.ts`) is the integration with The Graph Network itself: a step node that POSTs a GraphQL `query` and an optional JSON object of `variables` (both template-resolvable, the query edited as code in the settings panel via `contentMediaType: application/graphql`) and outputs the response's `data` object on its `data` handle, so the next node reads `{{input.<its handle>.<entity>.<field>}}`. `subgraph` is a Subgraph ID (queried at `/api/subgraphs/id/<id>`), a deployment ID (`Qm…`, `/api/deployments/id/<id>`) or a full query URL used as given. The key never travels in a flow: the engine reads `RunOptions.graph` (`{ apiKey, url? }`), which the API fills from `GRAPH_API_KEY` (a Subgraph Studio key, sent as `Authorization: Bearer`; `GRAPH_GATEWAY_URL` replaces the origin `https://gateway.thegraph.com`) on every run path (`engineFor` in `app.ts`, the run and session routes, the scheduler). Without the key the node fails its run as unconfigured; 401 or 403 reports a rejected key, another status names the gateway, and GraphQL `errors` are reported as the query's. The AI agent's `query_subgraph` tool is the same client bound to the one subgraph in the agent's config. The automatic checks on AI drafts have no fixture for the node, since its shape depends on the query, so a draft using it is reported untested from that node on. The curated "Uniswap pool watch" example (`apps/web/src/builder/examples.ts`) queries the Uniswap v3 mainnet subgraph for the USDC/WETH pool's `token0Price` and posts to Discord above a threshold.

Saved nodes are private node presets: `GET /node-presets` lists the caller's, `POST /node-presets` stores one from a node's type, label and config, and `DELETE /node-presets/:id` removes it (`packages/contracts/src/node-presets.ts`, `apps/api/src/node-presets/routes.ts`, behind the auth guard and the secrets rate limit). `redactPresetConfig` resets every field the node's schema marks secret before storing, so a preset carries `{{secrets.name}}` references but never a pasted credential; the cap answers 409 `conflict`. Inserting one copies the config into a new node, so neither side changes with the other, and the canvas's own validation reports a table, column or input the copy can no longer reach.

## Data tables

An account owns tables of records. `automator_data_tables` holds the table with its columns as JSONB, `automator_data_records` holds the rows with their values as JSONB keyed by column id (migration `0014_data_tables`, both cascading from the owner and the table). A column has an id, a name, one of six types — text, number, checkbox, datetime, single select, wallet address — and a required flag; ids are stable, so renaming a column breaks nothing and removing one drops it from the schema while leaving the stored values untouched. The stores enforce 50 tables per owner and 50 columns per table under the owner row lock, 50,000 records and 100 KB per record under the table row lock, and refuse a column type change once the table has records (`packages/db/src/data-tables.ts`, `data-records.ts`). Record listing is keyset-paged on `(created_at, id)` like runs; `find` evaluates the shared condition operators over the JSONB values; `dataColumnOperators` says which operator each column type accepts, the node settings offer only those, and the executors refuse the rest before the query runs.

`PATCH /data/tables/:id/records/:recordId` takes either shape: values alone replace the record, while `merge: true` changes only the named columns (`null` clears one) under the record's row lock, so an inline cell edit keeps the columns it does not touch; an `expectedUpdatedAt` that no longer matches the stored record answers 409 `conflict` instead of overwriting the other change (`mergeRecordValues` in contracts, `dataRecords.merge` in the store). `apps/api/src/data/routes.ts` exposes the owner-scoped CRUD (`/data/tables`, `/data/tables/:id`, `/data/tables/:id/records`, `/data/tables/:id/records/:recordId`); writes are rate limited and validated with `validateRecordValues` against the table's current columns before `normalizeRecordValues` stores them. Deleting a table that flows reference answers `{deleted: false, usedBy}` until the request repeats with `?confirm=1`.

Flows reach records through four nodes — `data.create-record`, `data.find-records` (branching `found` / `empty` with `{records, count, first}`), `data.update-record` and `data.delete-record`, the last two targeting a record id or a filter's first match. The engine never touches Postgres: `packages/flow-engine/src/data.ts` declares a `DataProvider` seam beside the chain seam, and `apps/api/src/data/provider.ts` implements it bound to one owner, so a table id from another account resolves to nothing. In `dry-run` the nodes read real data and report the write they would have made without performing it; the provider refuses writes in that mode as a second guard. Forking a marketplace listing clears the data nodes' table references, and `findFlowConfigProblems` marks a node whose table or column no longer exists so the canvas shows the badge. The AI composer receives the requesting owner's tables in its system prompt and may only use those ids.

In the web app, `/data` lists the tables and `/data/[tableId]` lists its records with the same keyset paging; columns and records are edited through dialogs generated from the column schema by the shared schema-driven form engine in `apps/web/src/components/schema-form/`, which also renders node settings and the builder's table and column pickers. Values are also editable in place (`record-cell.tsx`): a cell opens the editor its column type reads — text, number, datetime, a select, or a checkbox that saves on toggle — Enter saves, Escape cancels, and each save sends only that column with the record's `updatedAt`, so it keeps the other columns and reports a record changed elsewhere instead of overwriting it. A refused save keeps the draft in the editor with its reason beside the cell.

## Marketplace

A listing is a public snapshot of one of the caller's saved flows, so publishing never exposes later edits until the owner publishes again. Behind the auth guard, `GET /marketplace` lists every listing newest first, `GET /marketplace/:slug` returns one with its snapshot, `POST /marketplace` publishes the flow named in the body (the API mints a slug from the name, adding a numeric suffix when taken, and a second publish of the same flow updates the listing in place and keeps the slug), `DELETE /marketplace/:slug` removes the caller's listing, `POST /marketplace/:slug/fork` copies the snapshot into a new flow for the caller and answers 201 with the record, and `GET /flows/:id/listing` tells the builder whether a flow is listed. Input that fails the schema answers 422 `invalid_listing`; a user without a username (not onboarded) answers 403; a flow or listing the caller does not own answers 404. Before the snapshot is stored, `redactFlowSecrets` (contracts) resets every config field whose schema carries the `secret: true` marker (see `node-config.ts`: `secretFields`, `redactSecrets`), such as Discord webhook URLs, so a listing never carries the publisher's credentials and a fork shows those fields as "set your own"; the detail page carries the snapshot for a read-only graph preview; the public read behind `GET /public/flows/:id` returns no document at all, since the mini-app runtime plays a published flow through server-side sessions. In the web app, Server Components read listings through `apps/web/src/marketplace/server.ts` and merge them with the curated examples, `/marketplace/[slug]/fork` forks through the API and redirects to the new canvas, and the builder's publish dialog calls the same-origin handlers under `apps/web/src/app/api/marketplace`, which forward the browser's Privy bearer token. `packages/db` carries a `seed:marketplace` script that fills a development database with demo community listings for a populated page; their authors are `did:seed:*` ids no Privy login can reach and their fork counts are chosen numbers, so nothing it writes is usage data.

## Mini-apps

A flow that starts with `trigger.miniapp-open` is a mini-app: the visitor opens it and moves through its `screen.*` nodes (page, form, confirmation, QR code), each button choosing an output port, and the nodes wired between two screens run on `packages/flow-engine`; an unwired port ends the flow. A published flow runs on the API through sessions: `POST /public/flows/:id/sessions` runs it as the owner (with the owner's secrets and chain access) from the mini-app trigger to the first screen, stores the run in the owner's history with source `miniapp`, and answers a session id, a one-time token, and only the current screen (`nodeId`, type, label, its parsed config) plus the steps worked through; `POST /public/flows/:id/sessions/:sessionId/answer` takes `{ token, port, data? }`, resumes the run from that screen with the visitor's answer, stores that run too, and answers the next screen, `end`, or `failed`. A failed session never carries a node's error text (it can name URLs, addresses, revert data or secret names; the stored run keeps it for the owner's canvas and `/runs`): it answers `error` set to one sentence chosen by `visitorFailureMessage` in `packages/contracts/src/sessions.ts`: `miniAppFundsFailureMessage` ("This app can't send funds right now. Its owner has to finish setting it up first.") when the failing node signs with the owner's wallet and its failure classifies as `unconfigured` (server signing off, no signer on the API, no chain), otherwise `miniAppFailureMessage` ("This app hit a problem and could not continue."); plus a `code` the runtime can act on (`node_failed`, or `unconfigured`, `cancelled` and `timeout`, classified from the engine's error text in `failureCode`), and `help` when the flow owner filled the mini-app trigger's `visitorErrorMessage` config (for example how to reach them); the `steps` list names what ran and whether it failed, without errors. The document never leaves the API; sessions live in `automator_sessions` (token hash, waiting node, `vars`, opening payload, last run). A wrong token and an unknown session both answer 404; a session that already ended answers 409. Publishing is the owner's consent, so sessions run whether or not the flow's unattended triggers are enabled. The runtime renders a mini-app at `/a/[flowId]`, edge to edge on a phone and as a phone-sized card on wider viewports: the page reads the flow's public summary server-side (`GET /public/flows/:id` answers only id, name, description and update time), then the `RemoteMiniApp` component plays the session through the runtime's same-origin handlers under `/api/a/[flowId]/sessions`; a failed session renders `VisitorFailedView` inside the phone frame ("Something went wrong", the sentence, the owner's note, and a "Try again" button that starts a new session), and an API that cannot be reached or answers `rate_limited` renders the same view with its own sentence. With `?preview`, the document arrives from the opening builder window and plays on the in-browser engine (the owner's own unsaved canvas; `{{secrets.*}}` stay unresolved there). That in-browser `MiniApp` (the builder's screen preview and the `?preview` popup, both the owner's own view) settles a failed run to the same visitor sentence, shown first, with the node's own error beneath it for the owner. The web app's `NEXT_PUBLIC_RUNTIME_URL` names the runtime origin; the runtime's server-only `WEB_URL` pins the trusted builder origin. The handoff preserves real integrations and permits reloading the same popup while the builder remains open. Copied links cannot recover its in-memory document; published mini-app links provide visitor sharing. An unpublished URL without `?preview` shows App not found.

Three identity screens pause a mini-app the way `screen.*` nodes do, but the API derives their answer from a verified sign-in or proof rather than from what the browser sends (`data` is ignored on them). `privy.login` (config: title, message, button, allowed `methods`, a `simulate` visitor) answers with `privyToken`; the API verifies it and continues on `user` with `{ userId, wallet, email, loginMethod }`, also kept in `vars.visitor` for every later node (see Auth). `world.id-verify` (config: title, message, button, the Developer Portal `action`, `verificationLevel` orb or device, an optional `signal` template resolved against `vars` and `trigger`, and which branch `simulate` takes) is served with a `world` request context the API signs for that action (`WorldRequest`: app id, environment, `rp_context`), and answers with `worldProof`, the result IDKit produced; the API checks the result names the same action and, when a signal is configured, the same signal hash, forwards it to the Developer Portal (`POST https://developer.world.org/api/v4/verify/{rp_id}`, `apps/api/src/world/verify.ts`) and continues on `verified` with `{ nullifierHash, verificationLevel, action }` (the credential the portal accepted, such as `proof_of_human` or `device`) or on `rejected` with the portal's `{ code, detail }`; a portal outage answers 503 so the visitor can retry. An API without World or Privy configuration fails the node as unconfigured, recorded in the run like a model-less AI node. In the runtime, `identity-host.tsx` wraps a published mini-app with the Privy provider and IDKit's request widget (`@worldcoin/idkit`, dynamically imported), opening a QR code in a browser and completing natively inside World App, where the page also installs MiniKit (`@worldcoin/minikit-js`) on load. While a request is open the host swallows backdrop clicks and Escape in the capture phase (`isIdKitBackdropClick`, `isIdKitEscape`), so only the modal's own close button dismisses it: a closed request stops polling, and World App would report success to a page showing nothing. The World Developer Portal offers no verification webhooks, so `world.verification-completed` stays a plain trigger that nothing feeds (Simulate starts it with its sample payload; the webhook route only starts flows from a `trigger.webhook` node). A `world.id-verify` screen carries the request context it was served with, signed for five minutes; a visitor who lets it expire is told to reload the page, which starts a new session.

`world.selfie-check` is the third identity screen and World's Selfie Check (Beta) credential (issuer schema 11): a medium-assurance liveness and face-similarity check anyone with World App can complete, with no Orb visit, meant as a fairness and abuse-prevention signal such as one payout per live person rather than as proof of uniqueness across apps. Its config is the id-verify one without a level (title, message, button, `action`, `signal`, `simulate`). It shares the id-verify request path end to end: the API signs the same `WorldRequest` for its action, the runtime asks IDKit with the `SelfieCheckLegacy` preset instead of `ProofOfHuman` or `DeviceLegacy` (`apps/runtime/src/app/a/[flowId]/identity.ts` builds the ask as data, `worldAsk` / `selfieCheckAsk`), and the same verifier posts the result to the portal and accepts only a successful `selfie` result (World App's older `face` name is reported as `selfie`). The credential itself is World ID 3.0, so the proof comes back as a `3.0` result; IDKit 4 still requests it through the signed `rp_context` because the screen allows legacy proofs. The outputs are shaped as a gate: `verified` carries `{ verified: true, nullifierHash, credential, action }` and `rejected` carries `{ verified: false, code, detail }`, so a following `logic.condition` on `{{input.value.verified}}` reads either branch, and the nonce, expiry and unconfigured handling are the ones id-verify has. The curated "Selfie-gated claim" example wires it as Privy login → Selfie Check → condition → `usdc.payout` to the visitor's wallet. `docs/world-selfie-check-feedback.md` records what integrating it was like.

`usdc.payment` is the fourth screen the API prepares rather than merely serves, and the only one where the visitor spends their own money: it collects a USDC payment instead of sending one, while `usdc.payout` remains the outgoing transfer the owner signs. Its config is `title`, `description`, `amount` (in dollars, templated) and `to` (blank collects into the owner's own embedded wallet); its ports are `paid` and `declined`, and both branches carry `paid` (`true` with `{ txHash, from, to, amount, chainId }`, or `false`) so one `logic.condition` reads either. Because the visitor pays, the node signs nothing for the owner and is not in `signerNodeTypes`: a flow whose only funds node is a payment publishes and activates with server signing off. Serving the screen resolves the transfer server-side and sends it as `MiniAppScreen.payment` (`chainId`, `chainName`, `token`, `decimals`, `to`, `amount`, `amountUnits`), so the browser signs numbers it did not derive; a screen whose payment cannot be resolved (no chain, no USDC for it, no owner wallet, an unparseable amount) fails that node instead, and the visitor reads `miniAppPaymentFailureMessage`. The runtime's `identity-host.tsx` adds the `usdcPayment` actions to `IdentityActions`: `wallet` reads the paying wallet's balance over the chain's public RPC without ever prompting, and `pay` signs the visitor in if needed, switches their wallet to the payment's chain, sends an ERC-20 `transfer` through the wallet's EIP-1193 provider, and answers the screen with `port: "paid"`, `data: { txHash }` and a `privyToken`. Which wallet pays has to agree with `describeVisitor` on the API (the Privy embedded wallet, else the first Ethereum one), because the API verifies the payer. On answer the API recomputes the recipient and the units from the document, waits up to 60 s for the receipt (`ConfiguredChain.payments`, a viem `waitForTransactionReceipt` that decodes the ERC-20 `Transfer` logs), and accepts only a successful receipt carrying exactly one transfer of that chain's USDC, for that exact amount, to that recipient, from the wallet of the Privy user whose token came with the answer (`checkVisitorPayment`). It then records the transfer and claims the screen in one transaction (`sessions.claimWithPayment`, table `automator_payments`, migration `0018_payments`, unique on `(chain_id, tx_hash)`) — money the owner receives, kept apart from the two tables that bound what the owner sends, `automator_payment_policies` and `automator_payment_reservations` (see Onchain), which a visitor payment never touches, which is what stops one payment from answering two screens. Nothing here ends the session: a receipt that has not landed answers 409 `payment_pending`, a transfer that has already been used 409 `payment_used`, and one that does not match 400 `payment_rejected`, each of which the runtime shows as a notice above the same screen so the visitor can pay again. Simulate and dry runs auto-answer the screen with a sample transfer marked `simulated: true`, on the branch the node's `simulate` setting names. A fresh visitor wallet still needs the chain's native coin for gas: Privy's embedded wallets cannot sponsor it on this path, and gas sponsorship (ERC-4337 smart wallets or EIP-7702 with a paymaster) is not built.

## Account

`GET /account/usage` (`packages/contracts/src/account.ts`, `apps/api/src/account/routes.ts`, behind the auth guard) answers the caller's `AccountUsage`: flow and active-flow counts, stored runs started in the last thirty days by source, secrets and listings, plus the window's start. The web app reads it through the same-origin proxy `apps/web/src/app/api/account/usage`, which forwards the browser's Privy bearer token like the other proxies, for the Settings page's Usage section.

## Secrets

Node config references credentials as `{{secrets.<name>}}` rather than holding them. Secrets are per user (`automator_secrets`: owner, name matching `^[a-z][a-z0-9_]{0,63}$`, ciphertext, timestamps) and encrypted in the API with AES-256-GCM under `SECRETS_KEY` (32 bytes, base64; required in production, generated per process with a warning in development) before the database sees them; a stored value is `v1.<iv>.<tag>.<ciphertext>`. `GET /secrets` lists names, `PUT /secrets/:name` creates or replaces a value, `DELETE /secrets/:name` removes one; no route returns a value. The engine resolves secrets per node through `RunOptions.secrets` (a `SecretsResolver` the API builds for the flow's owner from `createSecretsResolver`), reading only the names that node's config references; a referenced name the owner has not defined fails the node. Without a resolver, as in the builder's in-browser preview, the placeholder stays literal. Every server-side run path (`/flows/run`, `/flows/:id/runs`, webhook and schedule triggers, the onchain-event listener, mini-app sessions) passes the owner's resolver. A `logic.set-variable` node that copies a secret into `vars` puts it into the run result, which the owner can read back.

Completed results are retained across screen pauses. On continuation, successful nodes forward their saved outputs without executing again or emitting new execution events; pending branches can then join those outputs with the visitor’s answer. Browser previews keep this checkpoint in memory. Server sessions read their owner-scoped `lastRunId` snapshot, continue its original document even if the flow was republished, and refuse to resume if that snapshot is missing.

For each executes an isolated Item subgraph. Nodes reachable from Done, including joins shared with Item, belong to the post-loop path and run once after the final iteration. Nested loops apply the same boundary within their parent body; screens are allowed on Done paths but not inside a loop body. Incoming edges from outside an Item body are rejected before execution; store shared values in variables before entering the loop instead.

Failed nodes can retain checkpoint outputs for audit: completed AI tool steps and transaction hashes already returned by the signer remain visible after a later failure or cancellation. Those outputs never activate downstream edges. Cancellation cannot undo a transaction that has already been submitted.

## AI

AI runs over OpenAI-compatible chat completions with plain `fetch`, behind one seam: `packages/flow-engine` defines `LanguageModel` (a chat request of messages, optional tools and a response format, answered with text and tool calls) and receives it through the executor context like `fetch`, so the engine stays browser-safe and tests script the model turn by turn with `scriptedModel`. `apps/api/src/ai/client.ts` implements the seam; `OPENROUTER_API_KEY` and `OPENROUTER_MODEL` (default `openai/gpt-oss-120b`, which supports tools and JSON-schema answers and costs a few cents per million tokens) are optional in every environment. `OPENAI_API_KEY` and `OPENAI_MODEL` (default `gpt-5.6-luna`) add OpenAI's own chat completions through the same client, composed by `withFallbackModel(openAi, openRouter)`: OpenAI is asked first, because the OpenRouter default reasons before it answers and kept losing its budget, and OpenRouter answers whenever OpenAI fails with any model error (unreachable, an error status, a timeout or an unreadable answer), so a run or a generation survives a free model going down; with only an OpenAI key it is the sole model. Without either key the API passes no model: AI nodes then fail their run as unconfigured and the AI turn route answers 503 (reading, patching and clearing a conversation still work). Model failures are mapped to `unconfigured`, `timeout`, `upstream` or `invalid_response` and never echoed to clients.

When `OPENROUTER_MODEL` ends in `:free` (or is `openrouter/free`), the client sends an ordered OpenRouter `models` list of at most three distinct entries: the selected model, a free alternative, and `openrouter/free` last. Candidates are Nemotron 3 Super and Gemma 4 31B; the router covers changes to the free catalog. `provider.require_parameters` keeps required tools/response formats, and a zero prompt/completion price ceiling keeps this path free. OpenRouter handles upstream failover inside the single model-call timeout (`modelTimeoutMs`, 130 s; one agent turn is bounded end to end by `requestBudgetMs`, 285 s). An explicitly selected paid model retains its single-model request.

`ChatRequest.onText` is the streaming seam: a caller that passes it is handed each content delta as the provider writes it, and the client then asks for `stream: true` and reads the `data:` lines of an OpenAI-style streamed completion through the same `fromWire` as a whole answer, so a malformed stream fails identically to a malformed body. Text already delivered cannot be taken back, which shapes both wrappers: `withFallbackModel` stops falling back once the primary has streamed a word, keeping that half-written turn rather than pasting a second whole answer onto it, and `withRequestDeadline` forwards nothing once its race is settled, so an abandoned call still streaming to its own timeout cannot write into the turn that moved on. A request carrying tools also carries `reasoning_effort: "none"` when it goes to OpenAI, whose chat-completions endpoint otherwise refuses function tools outright — `gpt-5.6-luna` refused every hop until this was sent.

Four node types run on it. `ai.generate-text` sends optional instructions plus a templated prompt and outputs `text`. `ai.classify` asks for one of the configured labels with a JSON-schema response format, rejects anything outside the set, and outputs `label` plus a handle named after the label. `ai.extract` takes a JSON schema as text, asks for a matching object, and checks the answer against a small in-engine matcher (type, enum, const, properties/required, items) before outputting `data`. `ai.agent` is a constrained tool loop: the config names the tools it may use from a fixed allowlist (`http_get` to configured hosts over https, `set_variable`, `discord_message` to the configured webhook, `query_subgraph` against the one subgraph named in the agent's `subgraph` config, answered as JSON cut at 4,000 characters), the model only ever sees those tools, `maxSteps` caps the turns, a disallowed tool or host is answered to the model as an error rather than executed, and every call is recorded in the node's `steps` output so a run can be audited and a test can assert the exact sequence.

The builder's AI panel is one conversation per flow, stored and streamed. Four routes sit under the flow (contracts in `packages/contracts/src/ai.ts`, handlers in `apps/api/src/ai/routes.ts`, ownership enforced as for every `/flows/:id/*` route): `GET /flows/:id/ai/messages` answers the conversation oldest first, `POST /flows/:id/ai/messages` sends a user message and answers `text/event-stream`, `PATCH /flows/:id/ai/messages/:messageId` sets a proposal's state to `applied` or `discarded`, and `DELETE /flows/:id/ai/messages` clears the conversation. The `POST` body is `{ text, document?, replace?, context? }`: `text` is the user's message (1 to 4000 characters), `document` the canvas as it stands when an existing flow is being edited, its secret config fields blanked by the builder (`redactFlowSecrets`) and blanked again by the route, `replace` the panel's new-flow mode saying to ignore the saved document, and `context` what the panel's context strip shows — `selection` (node ids), `problems` (the builder's `FlowProblem[]`) and `run` (a run's status, trigger, node results, run-wide error and the node to explain, passed through `redactRunOutputs` on both sides). Without a document the API reads the saved flow, while `replace: true` and an empty canvas both mean a new flow the model designs from nothing and answers with as a replacement. The browser never calls the API directly: same-origin Next route handlers under `apps/web/src/app/api/flows/[id]/ai/messages` forward the bearer token, and the `POST` one is the only streaming proxy in the app — `request()` always reads a body as JSON, so it uses a plain `fetch`, relays the upstream body untouched and carries the client's own abort upstream (`AbortSignal.any` with the request budget as its ceiling).

Migration `0020_flow_ai_messages` creates `automator_flow_ai_messages` (`id`, `flow_id` referencing `automator_flows` on delete cascade, `role`, `parts` jsonb, `context` jsonb, `created_at`), indexed on `(flow_id, created_at, id)`; `packages/db/src/ai-messages.ts` appends, lists and clears, and rewrites a message's `parts` in one correlated-subquery `UPDATE` so a state change happens under the row lock rather than as a read, a mutation in JavaScript and a write. A user message stores its text plus the context it carried, so a reload shows which nodes it was about; an assistant message stores its parts in arrival order, and a proposal part carries a `state` of `pending`, `applied`, `discarded` or `stale`. `PATCH` changes only that state, and only on a proposal still `pending`, so a decision already taken or superseded stands; sending a new message marks every still-pending proposal `stale`. The model's history is rebuilt from the last twelve messages: user text and assistant text, each cut to 1500 characters, and each assistant turn's tool calls with their results as chat tool messages, replayed whole. Proposal documents are never replayed; the current document is.

`apps/api/src/ai/canvas-agent.ts` runs the turn. The model works on a `WorkingCopy` of the document (`working-copy.ts`) through nine tools (`tools.ts`): `add_node`, `update_node`, `remove_node`, `connect`, `disconnect` and `set_flow` change the flow, `add_test` adds one behavioral scenario for the checks, `ask_user` ends the turn with a question of up to four options, and `suggest_next` offers up to three follow-ups. Every mutating call is validated the moment it lands: the node type must be in the generatable allowlist (executor types plus the engine-managed `logic.for-each`), handles must be real ids from `flowNodePorts`, config is cleaned through the node's schema (`parseNodeConfig`), each input handle takes one edge, a node cannot connect to itself, an edge that would close a cycle is refused, and a flow is capped at 80 nodes; a rejected call leaves the copy untouched, so a bad `chainId` never lands a half-applied rename. The refusal's message goes back to the model as that call's tool result and the loop continues, so it fixes the one thing rather than re-emitting a document. The loop is capped at 40 calls and shares one wall-clock `requestBudgetMs` deadline with every model hop and the checks. The system prompt (`prompt.ts`) is the node types with their handles and complete config schemas, the graph and template rules, the account's data tables and the execution limits, written for tools: prose and no tool call when the request is a question, `ask_user` and stop when one clarification is needed first, `suggest_next` once after a turn that changed the flow, and a short Markdown answer for the user rather than pasted JSON.

A turn whose working copy never changed is the model's prose and nothing else, so a question or an explanation produces no proposal; an `ask_user` call ends the turn where it stands, so a question is never paired with a draft. Otherwise the API lays the copy out and puts it through the document checks (`materialize`: the document schema, the referential checks, handle ids, one edge per input, a trigger, no orphans, no cycles, and the config problems the builder reports), and a failure is sent back to the model once inside the same turn as a "fix this" message — the one repair. A second failure still offers the draft, carrying a failed check and a warning not to turn the flow on, because a visible fault on the canvas beats a lost draft. A document that passes goes through `verifyFlow` on its own budget or what is left of the request's, whichever ends sooner, and the turn ends with a `proposal` event carrying the document, the verification report and whether it replaces the canvas. The model never receives a credential: applying an edit puts the canvas's own secret values back into the nodes it kept (`restoreFlowSecrets`), while a replacement inherits nothing and a secret the flow did not have stays blank for the user to fill in. The group frames never reach the model either, so the builder store carries them over instead (`keepGroups` on `setPreview` and `applyDocument`, `apps/web/src/builder/store.ts`): a drawn or applied edit keeps every frame that still has a node, re-adopts the nodes it kept and refits the frame around wherever they now sit, while a frame whose nodes all went is dropped.

The stream is one JSON object per `data:` line (`sse.ts`), each shape a member of `aiStreamEventSchema`: `message` names the assistant message first, `text.delta` carries the model's text as it is written, `tool.call` and `tool.result` open and close a step (a successful mutation's result also carries the laid-out working copy, which is what the canvas previews), `status` reports the phase the turn has reached (`checking` or `repairing`; the panel reads `thinking` until one arrives), and `question`, `proposal`, `suggestions`, `error` and `done` end it. The parts a message stores are the same shapes in the same order, so a reloaded conversation renders exactly as the live stream did: consecutive text deltas merge into one `text` part, and a successful `ask_user` or `suggest_next` becomes a question or suggestions part instead of a tool part, while a refused one stays a tool part carrying its error. A client that hangs up mid-stream stops the writes but not the turn, which still finishes and stores its assistant message. The request's own abort signal reaches the provider fetch, so Stop ends the model call rather than only the wait for it, and a turn that ended that way stores one error part whose detail is the shared `aiStoppedDetail` ("Stopped before the model answered.") — the same sentence the panel writes when it stops a turn itself, so a stopped turn reads the same live and after a reload.

Generated proposals also undergo semantic checks shared with the builder: form field ids must be usable and unique, template input handles must exist and be connected, and known form fields remain checkable through conditions and waits. The generation prompt includes complete nested config schemas, receiving-port examples, and execution limitations. Form mini-apps must include model-authored behavioral scenarios (two or more when branching). `apps/api/src/ai/verify-flow.ts` runs up to six scenarios against an allowlist of local executors, using QuickJS for code and visitor answers for screens. Network, wallet, identity and model-backed steps are not executed; a reached external step, or a flow containing a loop, is explicitly reported as untested. Execution is bounded to 80 nodes and 16 screen answers per scenario. Checks compare requested output values and resolved screen text, not merely run completion. The one repair covers the document checks, not these: a failed check is reported beside Apply rather than retried. Scenarios the model wrote badly, or checks that ran out of time, degrade to a warning on a draft that is still delivered, and the checks fall back to a sample run of the flow without those scenarios. Proposals carry a verification report shown beside Apply, including untested nodes and the distinction between sample execution and model-authored expectations. Those examples do not independently prove the user's intent or real external delivery. Non-finite numeric results from code fail in QuickJS before JSON can silently turn them into null.

Plain screen templates now resolve against the screen's receiving input handles, session variables and trigger payload in both the browser preview and server sessions. `screenScope` reconstructs fired inputs from retained run outputs, so values survive visitor pauses without exposing the full run to visitors. Browser previews retain this scope while refreshing screen copy from the document. Code still requires the server sandbox; these checks do not add browser code execution or publish a flow.

The canvas shows the draft while it is being built. The builder store holds `preview` (`apps/web/src/builder/store.ts`): `setPreview` hydrates the draft under the flow's own id, works out what the draft does to each node and edge (`previewKinds` over `diffNodes` / `diffConnections`: `added`, `changed`, `removed` or `kept`, published to each node as `data-draft`) and draws what the draft drops, faded, beside what it keeps. A preview freezes the document — every store action that would edit it returns early, so the canvas, the header, the hotkeys, the palette and the command menu go quiet together and undo and redo report nothing to do; only `applyDocument` is exempt. Opening a preview clears the real selection and the draft owns the selection while it is shown, so the panels follow the draft, and node settings open read-only for a previewed node (`readOnly={preview !== null}`). `preview` is set by every `tool.result` that carries a document and by the `proposal` event, and cleared by Apply, Discard, sending a new message and Start over; Apply calls `applyDocument` as one undo entry and fits the view. The node settings header's "Ask AI about this node" and the run panel's "Explain with AI" both go through `useAskAi`, which puts the node, the builder's problems or the redacted run into the panel's context and then focuses the composer or sends the message.

Home no longer asks the model itself: the hero prompt creates the flow (`createFlowAction` with `ai: true`, the button reads "Open on the canvas"), stores the text in `pending-prompt`, and the builder's panel sends it as the first message once the stored conversation has been read, so the stream is visible from the first second. A first turn that fails leaves a flow with a conversation in it rather than a dead end, on purpose. `AI_SCRIPTED_MODEL=1`, refused in production like `E2E_TEST_TOKEN`, builds the API with a scripted canvas model that answers any first message with the same two-node flow; the Playwright config sets it, and `apps/web/e2e/ai-chat.e2e.ts` walks Home to a streamed draft, applies it and reloads to find the conversation still there.

## Onchain

Chain access sits behind one seam like the language model: `packages/flow-engine` defines `ChainProvider` (chain id and name, a `reader` for calls, an optional `account` and `signer` for the user's wallet, a `mode`, and the chain's USDC address), injected per run through `RunOptions.chain` and exposed on the executor context. viem is a dependency of the engine for ABI parsing, argument coercion and unit maths, but no transport. The chains a flow may run on are the registry in `packages/contracts/src/chains.ts`: Base Sepolia (84532, `https://sepolia.base.org`, Circle USDC `0x036CbD53842c5426634e7929541eC2318f3dCF7e`, explorer `https://sepolia.basescan.org`) and World Chain Sepolia (4801, `https://worldchain-sepolia.g.alchemy.com/public`, Circle USDC `0x66145f38cBAC35Ca6F1Dfb4914dF98F1614aeA88`, explorer `https://worldchain-sepolia.explorer.alchemy.com`). A flow document's optional `chainId` picks one (the builder's flow settings; Base Sepolia when absent), and every run path (`/flows/run`, `/flows/:id/runs`, webhooks, the scheduler, mini-app sessions) asks the chain factory (`apps/api/src/chain/provider.ts`) for a provider on that chain: `resolveChainSettings` takes the registry, replaces a chain's RPC with `CHAIN_RPC_URL_<id>` when set, and still honours the older `CHAIN_ID` / `CHAIN_RPC_URL` / `USDC_ADDRESS` trio for the chain `CHAIN_ID` names (a per-chain URL wins over it; a `CHAIN_ID` off the registry is logged and ignored). Pointing a chain's RPC at a local `anvil --fork-url` makes that chain's live runs hit the fork with no code change; Foundry is not required for anything else. The provider carries the chain's name (`privy.wallet` outputs `chainName` beside the id and address) and its USDC address, so `usdc.*` nodes transfer that chain's USDC and fail with a message naming the chain where none is configured. The user's embedded wallet is the same address on every chain, and Privy signers are chain-agnostic, so a granted signer works on both.

`GET /wallet` (`apps/api/src/wallet/routes.ts`, contract in `packages/contracts/src/wallet.ts`, behind the auth guard) answers the caller's embedded wallet on one chain (`?chainId=`, the default chain otherwise): address, chain id and name, the native and USDC balances as decimal strings in their own units, and `signing`, whether the exact configured server signer is granted on the wallet, present only when the API has both its authorization key and signer ID. A chain off the registry answers 400, an account without an embedded wallet 404, and no chain provider or an RPC failure 503. `GET /wallet/transactions` (same plugin) lists what the caller's recent stored runs sent: it scans the newest 200 run records for transaction hashes in node outputs (`transactionHashes` in `packages/contracts/src/flow-runs.ts`, shared with the builder's run panel), takes the chain from the executed document, and answers at most 20 `WalletTransaction` rows (hash, chain, flow, run, node, time) newest first; 503 when runs are not stored. The builder and the `/wallet` page read both through the same-origin proxies under `apps/web/src/app/api/wallet`.

Writes run in one of two modes. `dry-run`, the default for Simulate, simulates the call as the user's wallet (`eth_call` plus a gas estimate) and answers `{ simulated: true, result, gas }` without broadcasting; reverts are decoded into the node error (`Reverted: NotOwner(0x…)`). `live`, which Simulate enables with its "Send real transactions" toggle and which trigger-driven runs always use, sends the transaction, waits for the receipt, and answers `{ hash, status, blockNumber, gasUsed, result }`; a reverted receipt fails the node. Reads never need a signer.

Signing uses Privy signers on the user's embedded wallet, the only option that serves both Simulate and unattended runs. One-time setup: an authorization key created in the Privy dashboard (Wallet infrastructure → Authorization keys), whose private key becomes `PRIVY_AUTHORIZATION_KEY` on the API and whose key quorum id becomes both `PRIVY_SIGNER_ID` on the API and `NEXT_PUBLIC_PRIVY_SIGNER_ID` on the web app. The API reads the wallet's current `additional_signers` once per provider/run, verifies its id, address and Ethereum chain type, and requires the exact configured signer; the broad `delegated` flag is not authorization evidence. The custom signing control verifies the grant through the API and refreshes on focus. Each user grants the signer once from the builder ("Enable server signing", `useSigners().addSigners`), after which the API signs through `createViemAccount` from `@privy-io/node` with a viem wallet client and no browser present. A run whose wallet lacks the grant, or an API without the key, fails the writing node with a message that says which of the two is missing; reads and dry-run simulations work with no Privy key at all.

Account-wide payment limits are stored by `packages/db/src/payment-policies.ts` in `automator_payment_policies`, with each admitted amount reserved in `automator_payment_reservations` (migration `0013_payment_policies`) and managed through authenticated `GET`/`PUT /wallet/payment-policy`. They default to disabled. An enabled policy specifies positive per-transfer and per-UTC-day limits for native ETH or the configured USDC on each allowed registry chain, plus an optional recipient allowlist; an unlisted chain/asset is blocked. Amounts use exact decimal strings and bigint base-unit arithmetic. Every server signer operation consults the current policy, including providers created before a settings change. The API adapter permits plain native sends and canonically encoded configured-USDC `transfer(address,uint256)` calls; other contract writes, message signing and offline transaction signing fail while limits are enabled. There is no human approval step.

Admission locks the owner's database row across workers and reserves the amount before calling the signer. The UTC day comes from the database clock after that lock. Reservations remain charged after failed or uncertain submission, and editing or disabling limits never resets them. Missing settings default to disabled; malformed stored settings fail closed. These limits measure the direct payment amount through Automator, excluding gas, activity outside Automator, and downstream recipient-contract effects or pre-existing token allowances. They are enforced by Automator's API, not a Privy platform policy. Read-only calls and payment dry-runs do not reserve budget.

Node types: `onchain.read-contract` and `onchain.write-contract` take an address, an ABI (JSON, or human-readable signatures one per line), a function name and a JSON array of arguments with templates, plus a native `value` for writes; integers in arguments may be strings. `onchain.transfer-token` sends the native coin or an ERC-20 (decimals read from the token). `onchain.sign-message` and `privy.sign-transaction` sign without broadcasting. `privy.wallet` outputs the user's address and chain id. `usdc.payout` transfers the configured USDC (six decimals) from the owner's wallet, `usdc.payment` collects it from a visitor's (a screen; see Mini-apps), and `usdc.balance` reads a balance, the user's own by default. Every output is JSON-safe: bigints travel as decimal strings.

## Environments and configuration

Development and production share one Railway PostgreSQL database; local development uses its public TCP endpoint with TLS, and the API uses the private connection URL. Copy each app's `.env.example` to `apps/api/.env`, `apps/web/.env.local`, and `apps/runtime/.env.local`. The web app holds two URLs for the API and they are not interchangeable: server-only `API_URL`, which on Railway is the API's private domain, and `NEXT_PUBLIC_API_URL`, which is inlined into the browser bundle and shown to anyone wiring up their own tools, so it has to be an address reachable from outside the private network — the `/v1` routes and `/mcp` are unusable without it. Privy configuration is split: web and runtime receive only `NEXT_PUBLIC_PRIVY_APP_ID` (the runtime's is optional and only serves `privy.login` screens); the API receives `PRIVY_APP_ID`, `PRIVY_APP_SECRET`, and an optional `PRIVY_VERIFICATION_KEY` for local token verification, required in production. World ID lives on the API only: `WORLD_APP_ID`, `WORLD_RP_ID` and `WORLD_RP_SIGNING_KEY` (the relying-party id and key the Developer Portal issues once World ID 4.0 is enabled for the app; all three or none) plus `WORLD_ENVIRONMENT`, which has to match the World App build visitors carry: `production` for the store app, `staging` for the simulator, `sandbox` for the TestFlight sandbox build (blank or anything else falls back to `production`); the runtime needs no World variable because each screen carries its signed request context. The Graph's two products are configured separately, both optional everywhere: `GRAPH_API_KEY` (a Subgraph Studio key, origin overridable with `GRAPH_GATEWAY_URL`) serves `graph.query-subgraph` and the agent's `query_subgraph` tool, and `TOKEN_API_KEY` (a Graph Market key, origin overridable with `TOKEN_API_URL`) serves `trigger.balance`; without the first, those nodes fail their run as unconfigured, and without the second, balance watchers stay idle and the scheduler logs why. Local values live in ignored environment files; Railway production variables are configured directly on their respective services. No secret belongs in frontend code or checked-in infrastructure configuration. Chain RPCs need no configuration: the API uses each registry chain's public RPC unless `CHAIN_RPC_URL_84532` or `CHAIN_RPC_URL_4801` names another (declared as preserved variables on the `api` service, since provider URLs often embed a key); the older `CHAIN_ID`, `CHAIN_RPC_URL` and `USDC_ADDRESS` remain an override for the one chain `CHAIN_ID` names.

API `/health` returns 200 when the database query succeeds and 503 when the database is unavailable or unconfigured. API `/health/live` and both frontends' `/health` only check their own process.

## Tooling and verification

Root scripts delegate to Turborepo for development, builds, production startup, type checking, and tests. Build outputs are `.next/` for each frontend and `dist/` for the API. Development and production servers are persistent, uncached tasks. Workspace dependencies propagate build/typecheck cache invalidation, and a transit task propagates lint invalidation through shared configuration packages.

Run `bun install` and `bun run dev` from the repository root to start web (3000), API (3001), runtime (3002), UI Lab (3003), and landing (3004); filter to one app with `bun run dev --filter=@automator/web`. Use `bun run lint`, `bun run typecheck`, `bun run test`, `bun run build`, and `bun run format:check` for verification; lint and build must pass before push or deployment. `packages/db`'s integration tests are the only ones that open a database connection and skip themselves when `TEST_DATABASE_URL` is unset, saying so and naming the command as they go (`integration-notice.ts`); run them against a scratch database before anything that changes the schema, because no memory fixture carries a constraint.

Bun's module mocks are process-wide and a whole-repo `bun test` shares one registry, so the last factory registered for `@privy-io/react-auth` defines it for every importer. Every web mock of the SDK therefore builds on the one shape in `apps/web/src/auth/test-privy.ts`, which must carry every name any app's product code imports; `apps/runtime/src/test-privy.ts` keeps the same union for the runtime, and a name added to one belongs in the other.

Oxlint runs React, Next.js, and accessibility rules for all four frontends and shared UI. Imports of the database package and configured database drivers, plus direct `process.env.DATABASE_URL` access, are lint errors in all four frontends and in UI, mini-app, flow-engine, API client, and contracts (`.oxlintrc.json` overrides). Oxfmt formats repository sources and configuration; READMEs, licenses, installed skills, and generated files are excluded.

Flow creation and updates write their version history in the same database transaction. Forks begin with version 1, and concurrent first publication updates one listing. Trigger configuration, type, removal and effective-chain changes clear stored event/watch state; label and layout edits preserve it. An opaque polling revision changes on executable edits and activation changes, including disable/re-enable and change/revert sequences. Before admitting execution the scheduler checks that revision; event cursor and watch writes take the flow-row lock and reject obsolete revisions. Watch observations also use compare-and-swap identity, and same-chain event cursors cannot regress. Cosmetic label, description, name and layout edits preserve the revision. An external operation already admitted cannot be undone by a later edit.

ABI overloads accept a canonical signature such as `transfer(address,uint256)` or a bare function name selected by argument count. Equal-arity overloads require a canonical signature or an ABI containing only the intended function; tuple and tuple-array signatures are supported. Named tuple arguments use the same safe integer and boolean conversion as positional tuples; large token amounts must be decimal strings. ERC20 transfers reject a false simulation result before broadcasting.

World session screens persist the issued request nonce and expiry. Answers must match that unexpired binding before portal verification; the atomic screen claim also compares it. Repeating a proof from another session is rejected without imposing global per-person action limits.

Execution limits bound work independently of node configuration: one `runFlow` invocation permits 10,000 actual node starts by default, shared across nested loops (`RunOptions.maxNodeExecutions` accepts a positive safe integer); replayed checkpoints do not consume that budget. An AI agent node permits 100 cumulative tool calls, refusing an oversized batch before any call in that batch executes. HTTP tool responses stop reading at 16,000 bytes and retain at most 4,000 characters, cancelling the remaining body. Earlier completed effects remain in audit checkpoints when a later limit fails.

Migration `0012_durable_trigger_claims` adds a persistent polling execution ledger and revision/observation fencing columns. Scheduler admission requires this ledger for schedules, onchain events and watches. An unresolved claim blocks new polling-trigger executions across the flow, including other trigger nodes and API instances; it never expires into an automatic retry or takeover. Only a completed matching occurrence is treated as a consumed duplicate. Execution records are retained independently when ordinary run-history storage fails, and the owner can inspect unresolved/unsaved outcomes in Flow settings. An abrupt crash before a provider returns may leave no transaction hash or intermediate output to reconcile; the durable claim still prevents automatic replay. Webhook requests and manual runs keep their existing semantics, and this is not a universal exactly-once guarantee.

`GET /flows/:id/trigger-issues` is owner-scoped and lists up to 50 retained ledger entries: unresolved executions and completed executions whose ordinary history write failed. Its shared TypeBox contract is validated by the same-origin web proxy. The Flow settings view refreshes every 15 seconds only while open, cancels pending requests on close/account changes, clears stale evidence on errors and offers Retry. Owners can inspect/download retained records; no release, retry or takeover endpoint is exposed. A running ledger row can represent either a live worker or a lost worker, so the UI does not infer a crash from elapsed time.
