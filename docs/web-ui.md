# Web workspace UI

Screen-level behaviour for `apps/web`'s `(workspace)` and `(canvas)` route groups. See `docs/architecture.md` for the app's place in the system.

## Shell and navigation

The sidebar and content layout are adapted from `arda.chat`: a fixed 260 px header inside a sidebar that springs between 260 and 64 px. That JavaScript width spring is the only animated value left; the surrounding content padding, top corner radius, and label opacities are CSS transitions keyed on the shell's state. A single `<Link aria-label="Automator flows">` carries both the mark and the wordmark and stays mounted across states, with the expand control positioned over it when collapsed. Flows, Runs, and Marketplace appear in the main navigation, each with a tooltip when the sidebar is collapsed. The root route (`/`) redirects to `/flows`, the workspace entry page. Sidebar state is restored server-side from a cookie through shared preference-cookie helpers (`apps/web/src/lib/preferences*`); Cmd/Ctrl+Shift+S, registered through a shared hotkey registry (`apps/web/src/lib/hotkeys.ts`), toggles it. A skip link precedes the shell for keyboard users. Reduced-motion preferences disable the layout animations. Links use the shared theme and Remix icons. The workspace shell has no dedicated narrow-viewport mode yet; mobile layout is out of scope for the current milestone.

Each workspace page's title renders as an `<h1>` beside a breadcrumb trail to its parents; `main` centers and caps page content. The workspace route group has shared `loading`, `error`, and `not-found` boundaries. `/flows/[id]`, the canonical flow URL, lives in the separate `(canvas)` route group, which verifies the session the same way but renders no shell: no sidebar, no header, the builder owns the whole viewport.

## Account menu and settings

The bottom account menu opens a responsive Settings dialog with Preferences, Connected apps, Usage, and Account sections. Theme selection works. Connected apps shows the Privy embedded wallet (shortened address from the session, with the builder's "Enable server signing" control, which reads "Server signing is enabled for this wallet." once the wallet carries the signer grant) and the notification channels the user has credentials for: Discord, Telegram and Email (Resend) each count as connected when one of the user's secret names contains `discord`, `telegram` or `resend` (`components/connected-apps.ts`, read from the shared secrets store, loaded when the dialog opens); a connected row names the `{{secrets.<name>}}` references, an unconnected one says "Not connected" with a hint to store the credential in a flow's Variables panel. No OAuth connections exist. Usage fetches `GET /account/usage` through the same-origin `/api/account/usage` proxy every time the dialog opens and shows a definition list: flows (with how many are active), runs in the last 30 days (total, with the Simulate, webhook, schedule, mini-app and onchain-event counts), secrets and published flows, with the date the run window starts. Usage limits and reset times are not configured or enforced. The tab list is vertical on desktop and horizontally scrollable on mobile, with keyboard navigation and focus restoration to the account trigger. The Account section reads the session directly and shows the profile name, username, and embedded wallet address with a copy-to-clipboard control. Log out clears the web session cookie first and only ends the Privy session once that succeeds. Its Dither Kit avatar is vendored in the shared UI package.

## Flows

Flow creation is available in the Flows header and empty state. Flows (`/flows`) has a responsive empty state with the shared icon illustration and four simple curated flow cards with node icons and integration logos, a short description, Automator attribution, and a Fork flow button; each card opens a `/marketplace/[slug]` detail page. Its presentation component accepts `FlowSummary` records (id, name, description, updated time) from `packages/contracts` and supports labeled grid/table view controls, name search, and sorting; the view preference is restored from a cookie. Flow cards and table rows show the name, the trigger kinds (catalog icons and label, or "No trigger"), the node count and the last-edited date. The page lists the signed-in user's flows from the API (`listFlows` in `apps/web/src/flows/server.ts`); a card opens `/flows/[id]`. Each card (on hover or focus) and table row has a Delete icon button that opens a confirmation dialog (`delete-flow-button.tsx`) naming the flow and warning that its listing and run history go with it; a successful delete refreshes the list from the server.

## Runs

`/runs` lists the signed-in user's most recent runs newest first (`run-history.tsx`): flow name, a status badge (Succeeded, Failed, Waiting), what triggered it (Simulate, Webhook, Schedule, Onchain event, Mini-app), start time and duration (`1.3s`, `12s`, `1m 05s`). A Coss select above the table (`run-filter.tsx`) narrows the list to one flow through `?flow=<id>`. A row links to `/flows/[flowId]?run=<id>`, which opens the canvas with that run's node results shown. Without runs the page shows an empty state pointing at Simulate on a saved flow, or at the triggers when a flow filter is active.

## Flow builder

`/flows/[id]` renders the builder edge to edge: a permanent 44 px sidebar on the left edge, a 260 px panel beside it, a middle column with a 44 px header above the React Flow canvas (an outline Simulate button on the left, joined by Stop and Restart icon buttons only while a simulation is running, and, on the right, a secondary Save button followed by an outline Publish button that opens the marketplace publish dialog), and a 360 px panel docked on the right that minimizes into a 44 px rail on its edge. Every bar shares one rhythm: 44 px of content plus a 1 px border outside it, an 8 px inset, and 28 px ghost icon buttons (Coss `icon-sm`) with 4 px between them, so every control lands on the same pixel row. The panel title rows, the canvas header, the sidebar, and the rail all use it, so the top rows line up and a rail's first control sits on that same row; titles are caption-size medium type. There is no breadcrumb or draft badge yet; the visual design is being redone from this reduced state.

The canvas draws dummy nodes from the catalog in `apps/web/src/builder/catalog.ts`: 36 types in seven categories (Triggers, Logic, Onchain, AI, Screens, Notifications, Integrations), none with a config schema yet. Type ids are `<kind>.<name>` for core nodes and `<provider>.<name>` for integrations (`world.*`, `privy.*`, `usdc.*`); a provider's trigger, such as `world.verification-completed`, is a trigger by category. Node cards use singular category names in the eyebrow, while the palette's headings use plural form. Every type declares named ports: triggers have no inputs, several types take two, branching types such as If/else have two outputs, and every type has at least one output. A card is a header plus a two-column grid of 24 px port rows, one handle per row, and an edge records the port it uses as `sourceHandle` and `targetHandle`. Edges are orthogonal (`smoothstep`). The palette adds a node on click (viewport centre, through `useAddNodeAtCenter`) or drag (pointer position, through the `application/x-automator-node-type` MIME type). Connections reject self-loops, duplicates, a second edge into an already-occupied input, and cycles. Delete/Backspace removes the selection, Shift-drag box-selects, a bottom-left panel zooms, fits the view and tidies up (moves every node onto the left-to-right grid of `packages/contracts/src/flow-layout.ts`, the same layout the AI generator uses, as one undo step), and a minimap sits bottom-right while the canvas has nodes. An empty canvas shows a note that every flow starts with a trigger, with a button that adds the mini-app trigger. The canvas shortcuts live in the hotkey registry's `canvas` scope (`use-canvas-hotkeys.ts`, mounted by the canvas header): Cmd/Ctrl+Z undoes and Cmd/Ctrl+Shift+Z redoes, Cmd/Ctrl+S saves, Cmd/Ctrl+Enter simulates, and Cmd/Ctrl+D duplicates the selected nodes with the edges between them, offset by 40 px and selected. Undo and duplicate stay quiet while typing in a field; save and simulate work everywhere. React Flow's attribution and minimap are hidden.

The side panels sit on the card surface, one step above the canvas in both themes. The sidebar's header slot holds a "Leave flow" icon link back to `/flows` under the same line as every other header. Below it, one ghost icon toggle per panel section (the active one shown pressed) picks what the left panel shows: Nodes (the catalog), Variables (the user's secrets by name, see below), and Outline (a node list with search for large canvases); and a separate "Flow settings" icon button pinned to the bottom opens the flow settings dialog. The left panel's title row shows the flow name as `h1`, with a small muted flow icon before it. Under Nodes the body is the node palette, a two-level catalog. Its resting state is the group list: a "Core" section with one row per kind (Triggers, Logic, Onchain, AI, Screens, Notifications) and an "Integrations" section with one row per provider (World, Privy, USDC), each row showing an icon or logo, a description, and the node count. Opening a group replaces the list with that group's entries under a "‹ All" back control and the group name; a provider's entries split into Triggers and Actions sections, so a provider's own trigger lives with its actions rather than under Core › Triggers. The search box above (matching labels and descriptions, case-insensitively) wins while it has text and shows flat results sectioned by group across the whole catalog; clearing it returns to wherever the palette was. A grid-view toggle beside the search switches node lists between rows (icon, label, one-line description) and three-per-row tiles (description in a tooltip). No match shows "No nodes match." with a Clear search link. Groups are declared in `catalog.ts` (`catalogGroups`, each entry carries a `group`), and the three views are the pure functions `listCatalogGroups`, `getCatalogGroupSections`, and `searchCatalog`. Search, open group, and view are component state and reset with the page. Outline (`flow-outline.tsx`) lists the flow's problems first (see below), then every node on the canvas with a search box; choosing either selects that node. Variables is empty until it is designed. The right panel's title row starts with a minimize control, and right-aligned Coss tabs (icon and label, 24 px tall in the 28 px list) switch between AI agent and Screen preview. Minimized, the panel becomes a right rail with one toggle per tab that reopens the panel on that tab. The state is not persisted.

The AI agent tab is a conversation about the flow (`apps/web/src/builder/ai-panel.tsx`). The thread lives in a per-builder zustand store beside the run store (`ai-store.ts`, mounted by `flow-builder.tsx`, never persisted, so loading another flow starts empty): user turns, assistant turns with the model's message or summary, and for each proposal its state. Messages render as a chat list with the composer at the bottom (Cmd/Ctrl+Enter or Send submits); an empty thread explains what a message does. Every request sends the canvas as it is now, after any applied proposals, plus the thread's earlier turns as the contract's `history` (texts and summaries only), so "also notify Discord" edits the current flow. An "Edit the current flow" checkbox shows once the canvas has nodes, ticked by default, and unticking asks for a new flow instead; an empty canvas reads "New flow" and needs no choice. An answer is either a plain assistant message (a question or an explanation, when the prompt asked for no change) or a proposal: the summary with a preview card listing node by node what applying would do against the canvas right now (Keep, Change, Add, Remove, with label and type), and "Apply changes" (or "Replace canvas" when a new flow would replace nodes) puts it on the canvas through the store's `applyDocument`, which keeps the flow id, marks the flow dirty, and fits the view; Discard drops it. An applied turn reads "Applied", a discarded one "Discarded", and applying one proposal marks the other pending ones "Superseded by a later change", since they were drawn from an older canvas. "Start over" clears the thread (a request still in flight is dropped when it lands). Failures show as assistant turns in the thread: no OpenRouter key on the API, a session that expired, a prompt the model could not turn into a valid flow, or more than the API's per-user AI limit in a minute ("Too many requests. Try again in a moment."). Explanations of a failed run (see the run panel below) arrive in the same thread.

Screen preview plays the canvas as its mini-app (`packages/miniapp`) inside a phone frame sized from the panel's height, on the real flow engine: the nodes between screens execute in the author's browser, so clicking through a form wired to a Discord message sends it. A tools row above it, on the palette's rhythm, says whether the preview runs from the trigger or from the selected screen (selecting exactly one screen node opens the preview on that screen), a Restart icon button, and an "Open in browser" icon link to the runtime's `/a/[id]?preview` with the current document encoded in the URL fragment. Adding, removing or rewiring nodes restarts the session; editing a node's config, or the flow name shown in the phone's top bar, updates in place, and the next run uses the edited document. A flow without a mini-app trigger shows "Not a mini-app yet" in the phone. Because this is the author's own preview (as is the runtime's `?preview` page), a failed step shows the node's label and its real error text, which the author needs; visitors of the published app never see it, they get the generic failure screen with the trigger's visitor message (see Mini-apps in `docs/architecture.md`). The identity screens (Privy login, World ID verify) render in the phone as they do for a visitor, but since neither Privy nor World can run against the author's session there, their button plays the node's sample answer and a note under it says so ("Preview: continues as visitor@example.com", "Preview: continues as verified"); the World node's `simulate` setting picks the branch.

The Variables section (`variables-panel.tsx`) lists the signed-in user's secrets as `{{secrets.<name>}}` with a delete control, and a form above them adds or replaces one (lowercase name, a password-type value that is never shown again); names load once per page through the same-origin `/api/secrets` proxies into a small shared store (`secrets-store.ts`) that the node settings picker reads too. Form errors show under it, including "Too many requests. Try again in a moment." when the API's per-user limit on secret writes is hit.

Selecting one node swaps the left panel's palette for that node's settings (`node-settings.tsx`): the label, then one control per property of the node's config schema from `packages/contracts`, written to the store as it is typed, with a property's schema `description` under the control as help text. Enums are selects, booleans switches, numbers and strings inputs (prose keys such as body or content get a textarea), string arrays one comma-separated line, arrays of objects an item list (each item a bordered group titled by its label or id, with move up, move down and remove, and an add button that fills the item schema's defaults), and nested objects a group. Arrays of a fixed literal set, such as the agent's tools or the Privy login's allowed methods, are checkbox groups (`multi-select-field.tsx`). A string property marked `contentMediaType: "application/json"` in its schema, today the triggers' **Sample payload**, is a monospace JSON textarea: the text is stored as typed and an inline "Invalid JSON" note (with `aria-invalid`) appears while it does not parse. Types without a schema only offer the label; the mini-app trigger offers a "visitor error message" that a published app shows visitors when it fails. The "Insert variable" menu lists, after the trigger's payload entry, one `{{trigger.<key>}}` per top-level key of the trigger's sample payload, expands an identity screen's answer into its fields (`{{input.<port>.email}}`, `{{input.<port>.nullifierHash}}`, …) and, below any Privy login, lists `{{vars.visitor.*}}`.

State lives in a per-page zustand store; `serializeFlow` turns it into the `FlowDocument` contract and `hydrateFlow` reverses it. Simulate (`use-flow-run.ts`) runs the saved flow through `POST /flows/:id/runs` while the store is clean, so the run lands in the history, and falls back to the stateless `POST /flows/run` with the canvas document while there are unsaved changes; both requests send the starting trigger's sample payload (`trigger-payload.ts`: the first trigger in document order without an incoming edge, its `samplePayload` config parsed, `{}` without one or when it is not valid JSON) as the run's trigger payload and `screens: "auto"`, so a mini-app flow simulates end to end with every screen answered by the engine (pills read "Auto-answered", the run panel "Answered by Simulate · <port>", and a form's inspector shows the sample values), while the mini-app runtime keeps waiting for real visitors; the result lives in a separate run store (`run-store.ts`), which `?run=<id>` on the flow URL seeds with a stored run. A run the API refuses shows a message in the run panel's place: an expired session, a flow that no longer exists, invalid settings, or "Too many requests. Try again in a moment." past the per-user run limit. The page loads the stored document from the API and remounts the builder per flow id and run; an id the user does not own renders the canvas group's not-found screen. Save (`save-button.tsx`) serializes the store, sends it to `/api/flows/[id]` with the Privy access token, and calls the store's `markSaved` on success; it is disabled while nothing changed since the last save, shows a loading state while saving, a muted "Saved" afterwards, and an inline error message (session expired, flow missing, invalid document, or unavailable) when the save fails. The Flow settings sidebar button opens `flow-settings-dialog.tsx`, which edits the name, description and **Chain** (a select over the registry in `packages/contracts/src/chains.ts`: Base Sepolia or World Chain Sepolia, where the flow's onchain nodes read, write and listen) in the store (Apply) so that Save persists them like any other change; the chain lands in the document as `chainId`. Below them sit settings that are not document state: an **Active** switch that saves through `PATCH /flows/:id` straight away and lets the saved flow's webhook, schedule and onchain-event triggers start runs; the flow's **Webhook URL** (on the web origin, with a copy button) whenever the canvas has a Webhook trigger node; a per-canvas **Send real transactions** switch that makes Simulate run onchain nodes live instead of as a dry run; under it the embedded wallet's balances on the selected chain (`wallet-funds.tsx`, read once per chain per dialog open through the same-origin `/api/wallet` proxy: the shortened address, the native and USDC amounts, and the warning "This wallet has no funds on <chain>." when both are zero; no faucet link); and the Server signing control. Activation and the webhook token reach the builder through `flow-activation.tsx`, seeded from the loaded record. The save controller is created once per builder (`SaveFlowProvider` in `save-button.tsx`) and shared by the Save button, Cmd/Ctrl+S and the unsaved-changes guard (`leave-guard.tsx`, decisions in the pure `leave-decision.ts`): while the store is dirty a `beforeunload` handler makes the browser ask before the tab closes, reloads or leaves for another site, and a plain click on an in-app link away from the canvas (the sidebar's "Leave flow", the publish dialog's "View listing") opens a Coss alert dialog, "Leave without saving?", with Stay, Leave (navigates without saving) and Save and leave (runs the shared save and navigates only when it succeeds; a failure shows its message in the dialog). Modified clicks that open a new tab pass through, a clean store navigates straight away, and the browser's back button is not intercepted. Forking an example builds its document on the server at `/create` from the hand-authored fixture in `examples.ts` (`exampleToFlowDocument` copies it with fresh ids).

The store keeps an undo history (`past`/`future`, capped at 50 entries): every document change opens an entry, a drag counts as one, deleting a node with its edges counts as one, consecutive edits to the same label, config field or flow setting coalesce, selection never enters history, loading a document clears it, and applying an AI result is undoable. Undo and redo mark the flow dirty.

Validation runs on every change (`validation.ts`, through `use-flow-problems.ts`): the contract's referential checks, a missing or unreachable trigger, nodes no trigger reaches, config the engine cannot read, config it refuses to run without (a variable name, a Discord message, a World action id), an empty form, a trigger sample payload that is not valid JSON (a warning: Simulate sends an empty one), and a World ID verify whose Rejected port is unwired (a failed verification would then end the flow as done). A blank secret such as a forked Discord webhook is a warning that reads "set your own". Cards show a badge (red for errors, amber for warnings, the messages in its tooltip) and an error tints the card border; the Outline lists every problem. With errors on the canvas, the first click on Simulate shows how many may fail the run and the first message, and the second click runs anyway.

After a run, the canvas shows the result in place: each node's status pill carries its elapsed time, edges that fired turn green and the ones that went dead are dashed and faded (`run-selectors.ts`), and a run panel (`run-panel.tsx`) docks to the bottom of the canvas with the run's outcome, total time, the trigger that started it, and the run-wide error the engine reports (for example a flow with no trigger), then every node in execution order with its status and elapsed time. Choosing a row selects the node on the canvas and shows its outputs per handle (an output carrying a transaction hash, such as a receipt, gets a "View on <chain>" link to the flow's chain explorer above the JSON), its error (with an "Enable server signing" button when the error says signing is not enabled, and the same "This wallet has no funds on <chain>." warning as the settings dialog when the error says the wallet could not pay), or why it was skipped; a screen that Simulate answered reads "Auto-answered" on the card and "Answered by Simulate · port" in the row; the panel opens on the failed node when there is one, can collapse to its title row, and clears with the run. A failed run offers "Explain with AI" in the title row and under the failed node's error (`use-explain-run.ts`): it posts the canvas document with its secret config fields blanked (`redactFlowSecrets`) and the run's results with outputs, errors and trigger payload passed through `redactRunOutputs` to `POST /ai/runs/explain` through the same-origin proxy, adds the question to the AI thread, and brings the AI tab in front; the answer lands there as an assistant message, or as a message with a proposal card and Apply when the model proposes a config or wiring fix. React Flow's own colour mode is unused; the builder tokens restyle it in both themes through `flow-builder.module.css`.

## Marketplace

`/marketplace` browses every published flow together with the eight curated examples: a search box (matching name, description, author, node type ids and category names), a segmented filter (All, By Automator, Community, Yours), a sort menu (Newest, Most forked, Name A–Z), and a row of category chips (Mini-apps, AI, Onchain, Notifications, Logic, derived from each listing's node types; a listing can be in several) above a four-column card grid that steps down with the container width. Each card shows the node types the flow highlights (drawn with their builder catalog icons), the name linking to the detail page, the description, the author (`Automator` or `@username`), the fork count for published flows, and a Fork flow button. Empty states name the situation: no matching search, no community flows yet, or nothing published by the current user. Sorting by newest puts published flows before the undated curated examples; the browse logic is the pure `browseListings` in `apps/web/src/marketplace/listing.ts`.

`/marketplace/[slug]` shows a curated example or a published listing: node marks, a byline (By Automator, or the author's name and username with the publish date and fork count), the description, Copy link and Fork flow buttons, a read-only React Flow preview of the graph (`apps/web/src/marketplace/flow-preview.tsx`: pan and zoom only, the builder's node cards), and a numbered "How it works" list. For published flows the steps are the document's non-trigger nodes, named by their labels and described by their catalog entries. Unknown slugs return not-found. Forking a curated example goes through `/create?example=`; forking a published flow goes through `/marketplace/[slug]/fork`, which asks the API for a copy and redirects to the new `/flows/[id]`.

Publishing happens from the builder's Publish button. The dialog loads the flow's current listing first, then offers "Publish to the marketplace" for a new one or "Update listing" (with an Unpublish action and an inline confirmation) for an existing one. It edits a listing name (up to 120 characters) and a description with a 280-character counter, warns when the canvas has unsaved changes because the listing is made from the last saved version, and on success shows Copy link and View listing. Failures name the cause: an expired session, an unfinished profile, a flow that no longer exists, or invalid input.

## Placeholders and dev tooling

There is no dedicated `/settings` route; the Settings dialog is the only entry point. The workspace shell does not fetch API health to render itself. Agentation is available in development only, using the same local annotation setup as UI Lab.
