# Web workspace UI

Screen-level behaviour for `apps/web`'s `(workspace)` and `(canvas)` route groups. See `docs/architecture.md` for the app's place in the system.

## Shell and navigation

The sidebar springs between 240 px and a 52 px rail; that JavaScript width spring is the only animated value, and the content padding, top corner radius and label opacities are CSS transitions keyed on the shell's state. Every mark, icon and avatar is centred on x = 26 px, the rail's own centre, so collapsing takes width away from labels without moving anything else. A single `<Link aria-label="Automator home">` to `/` carries the mark and the wordmark across both states, with the expand control positioned over it when collapsed. Navigation is three labelled bands: Workspace (Home, Flows, Runs), Resources (Data, Connections, Wallet) and Share (Mini-apps, Marketplace), with Settings and the account menu in the footer. A destination is current when the path equals its href or starts with it; collapsed, each row gets a tooltip. Runs carries the sidebar's one live number — runs that failed since midnight, counted in the workspace layout from a single page of failed runs, so the badge costs one request and an unreachable API simply leaves it off. Sidebar state is restored server-side from the `workspace_sidebar` cookie through the shared preference-cookie helpers (`apps/web/src/lib/preferences*`); Cmd/Ctrl+Shift+S, registered through the hotkey registry (`apps/web/src/lib/hotkeys.ts`), toggles it. A skip link precedes the shell for keyboard users, and reduced-motion preferences disable the layout animations. The workspace shell has no dedicated narrow-viewport mode yet; mobile layout is out of scope for the current milestone.

Inside it, `PageFrame` (`apps/web/src/components/page-frame.tsx`) owns every page's furniture, so no page improvises its own: a 48 px title bar holding the `h1` and the page's primary actions, an optional banner, a 44 px toolbar for filters and view controls, and a content region that scrolls on its own so both bars stay put. Nothing rules to the edge — the gutter is 24 px and the toolbar's hairline stops at it. A detail page passes `parents` and gets its section as a muted link ahead of the title on the same line. Home and Marketplace are the two pages without a title bar — each names itself in the middle of its own column instead — and the builder does not use the frame at all. The workspace route group has shared `loading`, `error` and `not-found` boundaries; the loading one renders the frame's shape rather than a bare spinner, and Home, Flows and Runs each carry their own. `/flows/[id]`, the canonical flow URL, lives in the separate `(canvas)` route group, which verifies the session the same way but renders no shell: no sidebar, no header, the builder owns the whole viewport.

## Account menu and settings

The bottom account menu opens a responsive Settings dialog with Preferences, Usage and Account sections. Preferences holds the theme selection and a Connections row whose "Open connections" button closes the dialog and goes to `/connections`, where the secrets and the apps they reach now live. Usage fetches `GET /account/usage` through the same-origin `/api/account/usage` proxy every time the dialog opens and shows a definition list: flows (with how many are active), runs in the last 30 days (total, with the Simulate, webhook, schedule, mini-app, onchain-event and watch counts), secrets and published flows, with the date the run window starts. Usage limits and reset times are not configured or enforced. The tab list is vertical on desktop and horizontally scrollable on mobile, with keyboard navigation and focus restoration to the account trigger. The Account section reads the session directly and shows the profile name, username, and embedded wallet address with a copy-to-clipboard control. Log out clears the web session cookie first and only ends the Privy session once that succeeds. Its Dither Kit avatar is vendored in the shared UI package.

## Home

`/` is the workspace entry page (`app/(workspace)/(home)/`) and the first of the two pages with no title bar: the hero takes 86% of the scrolling region's height, so the prompt owns the first screen and scrolling past it is a deliberate act. The hero (`home/prompt.tsx`) carries a WebGL backdrop vendored from React Bits (`home/hero-backdrop.tsx`, `vendor/web-threads/`), whose thread colours and ground are read from the palette tokens by painting one pixel and reading it back, so it follows the theme instead of carrying a second copy of the brand colour. Under the heading a textarea takes the sentence (Enter submits, Shift+Enter breaks the line, 4000 characters) and "Draft the flow" asks the model before anything is saved: the answer and the prompt are stored for the canvas and only then does the create action run, so a draft that fails or is stopped leaves no empty flow behind, and the builder's AI panel replays both on mount. While the request is in flight a status line counts the elapsed seconds against the clock and offers Stop; a failure shows the reason and keeps the sentence in the box to be rephrased.

Below it, "Start from an example" offers three curated flows that need no setup beyond a Discord webhook, forked and opened by the same action the marketplace uses, and a link to the rest. Under that, one stream (`home/activity.tsx`, in Suspense behind a skeleton): armed triggers in the future tense above the now line, what has already happened beneath it, grouped by the reader's own day. Only schedule, price, balance, onchain-event and webhook triggers count as armed — the rest wait for a person, so nothing is coming up. It shows a glance rather than a history (three upcoming rows, eight runs); a row is a link, and an unreachable API leaves the tape empty rather than failing the page.

## Flows

`/flows` (`flow-browser.tsx`) lists the signed-in user's flows from the API (`listFlows` in `apps/web/src/flows/server.ts`) on the page frame: name search and the New flow button on the title bar, the sort menu (Last edited, Name A–Z) and a grid/table toggle on the toolbar, with the view preference restored from the `flows_view` cookie. A card leads with the flow's own shape — a miniature drawn from its stored node positions (`flows/flow-miniature.tsx`), or "Empty canvas" — so the list is scanned by what each flow looks like rather than by a glyph every card repeats, and carries an Active/Inactive mark, the name, what starts it (one trigger says its own detail, several are only counted, none reads "No trigger") and how it last ended. The table view carries the same facts as columns. Each card (on hover or focus) and table row has a `…` menu with Open on canvas, View runs and Delete flow; Delete opens a confirmation dialog (`delete-flow-dialog.tsx`, controlled by the menu so it survives the popup closing) naming the flow and warning that its listing and run history go with it, and a successful delete refreshes the list from the server.

With no flows at all the page shows the shared icon illustration and three start cards (`flow-start-options.tsx`: "Describe it to AI" opens a new flow with the cursor in the AI prompt, "Start from an example" jumps to the curated cards below, "Start blank" opens an empty canvas), a link to the marketplace, and the curated example cards, each opening a `/marketplace/[slug]` detail page. A search that matches nothing offers to clear itself instead.

## Data

`/data` is one working surface rather than an index and a detail page. `data/layout.tsx` reads the
owner's tables once and renders three things side by side: the table rail, the section's content,
and a `@panel` parallel-route slot. `/data` shows the gallery, `/data/<table>` the records of that
table, and `/data/<table>/<record>` the same records with that record open in the panel — so one URL
carries the whole view, the panel can be linked, and Back closes it. Below 1000 px the open panel
takes the pane, as on Runs.

The rail (`table-rail.tsx`) is 200 px on `--card`: a `Tables` band label on the title bar's line,
one 30 px row per table with its record count, the open table marked `aria-current="page"` (a record
open in the panel still marks its table), and `New table` at the foot. Collapsing it, which rides
the `data_rail` cookie the way the sidebar rides `workspace_sidebar`, does not take the navigation
away — the list becomes a `Choose a table` menu in a 44 px strip.

The gallery (`data-browser.tsx`) gives each table a card that leads with its first four columns,
each with its type icon and type name, then the table's name, description and
`N records · M columns · edited`; a table with more columns than fit says how many are left, and one
with none still keeps its shape. Search and sort sit on the title bar and toolbar as on Flows.

The grid (`record-grid.tsx`) draws a row-number gutter, one header per column carrying the column's
type and a menu that sorts ascending or descending or opens a filter for that column
(`record-filter-dialog.tsx`, offering only the operators `dataColumnOperators` allows for that
type), values styled by type (`record-value.tsx`), inline cell editing (`record-cell.tsx`,
unchanged), an expand control per row that opens the panel, and a `New record` row. Filters and the
sort show as removable chips on the toolbar.

Filter, sort and search live in the URL (`record-query.ts`), so the server renders what the reader
sees and a narrowed view can be linked; anything unreadable in the URL is dropped rather than
refused. The two paging arms are distinct and the toolbar says which one is running: an unfiltered
table pages 25 at a time by cursor, while a filtered, sorted or searched one asks the API's `find`
path for at most 100 matches and reports `Showing the first 100 matches` when the response's
`truncated` flag is set.

The panel (`record-panel.tsx`) reuses the shared `SidePanel`: the record's label over when it was
last edited, every column as a labelled field through the same schema-form fields the table dialog
uses, and delete behind the panel's menu with its confirmation. Saving an edit carries the
`updatedAt` the reader saw, so a record changed elsewhere is refused with `conflict` rather than
overwritten. `/data/<table>/new` is the same panel in its create state, which is what `Add record`
opens; there is no separate record dialog.

## Connections

`/connections` is where the account's credentials and the apps they reach live; the Settings dialog only points at it. The page reads the secret names on the server (`apps/web/src/connections/server.ts`), so a value never travels to the browser — the API returns names and dates, and nothing else. The Secrets section pairs a form (a lowercase name and a password-type value, the same validation the builder's Variables panel applies) with one row per secret: its `{{secrets.<name>}}` template, when it was last saved, and a delete control. Saving and deleting go through the shared secrets store (`builder/secrets-store.ts`), so the builder's panel and this page never disagree, and the page then refreshes from the server.

The Connected apps section reads the same names: Discord, Telegram and Email (Resend) each count as connected when a secret name contains `discord`, `telegram` or `resend` (`components/connected-apps.ts`), and a connected row names the references it found while an unconnected one keeps the hint for what to store. No OAuth connections exist. When the API cannot be reached the page says the secrets could not load and offers to try again rather than showing an empty list, and it withholds the channel statuses instead of reporting apps as unconnected on evidence it does not have.

## Wallet

`/wallet` (`app/(workspace)/wallet/`) stacks four sections in the page frame and shows the embedded wallet: the full address with a copy button and an explorer link per registry chain, the server-signing status (a success badge, or the "Enable server signing" control with one sentence on why live runs need it), a Balances grid with one card per chain (native and USDC amounts, rounded for reading with the exact value on hover and set in tabular figures, "Unavailable" when that chain's RPC failed, and the "This wallet has no funds on <chain>." warning when both are zero), and a Recent transactions table (time, flow linking to the canvas with that run, node type, chain, short hash linking to the explorer) from `GET /wallet/transactions`, with an empty state until a live run sends one. Each chain is read on its own through `apps/web/src/wallet/server.ts`, so one unreachable RPC never fails the page; an account with no embedded wallet on any chain sees an empty state instead.

The Payment limits card is available with or without a loaded wallet. It saves account-wide rules through `/api/wallet/payment-policy`: an enable switch, an optional recipient allowlist, and per-transfer/per-UTC-day ETH or USDC amounts for each selected chain. Saving applies immediately without an approval step. The card shows today's reserved amounts, including uncertain attempts; absent chain/asset rules block that payment when enabled. Failed reads show Retry instead of editable defaults, account changes cancel stale requests, and edits made during a pending save remain unsaved. Limits cover direct Automator payments, excluding gas and outside activity; unsupported contract calls and signing-only operations are blocked while enabled.

## Runs

`/runs` and `/runs/<id>` are one screen. `runs/layout.tsx` renders the list beside a `@panel` parallel-route slot, so opening a run puts it in a 420 px panel next to the list it came from: one URL carries both, the panel can be linked, and Back closes it. The panel (`components/side-panel.tsx`) is not modal — the list stays readable and clickable, so moving between runs is one click — Escape closes it, and closing is a navigation back to the list exactly as it was filtered, ordered and paged. Below 1000 px the open run takes the pane and the list waits behind Back.

Above the list, a band (`run-stats.tsx`) says what the last two weeks did: `GET /runs/stats` counts runs by UTC day and outcome over a 14-day window — a page of runs is a window, not a history — and the band draws them as a stacked bar chart (`runs-chart.tsx` over `@automator/ui/dither-chart`), three tiles (runs, failed, succeeded as a percentage of finished runs) and a legend. Each series wears the token its status badge already wears, resolved from the palette at runtime through `useTokenSeeds`, and the legend names it, so outcome is never carried by colour alone. The band is absent when nothing ran or the API is unreachable.

The list itself (`run-history.tsx`) has no toolbar: every column heading carries its own order and, where the API can filter by it, its own filter, each as a link, so the list stays server-rendered. Started, flow, status, trigger and duration each sort with their own wording ("Newest first", "Longest first", "Name A–Z"), and the filters, the order and the page all live in the URL through `run-links.ts` (`?flow=`, `?status=`, `?sort=`, `?dir=`, `?cursor=`), so a narrowed list can be linked and opening a run keeps it. A row carries the flow name, a status badge (Succeeded, Failed, Waiting), what triggered it (Simulate, Webhook, Schedule, Onchain event, Watch, Mini-app), the start time and the duration (`1.3s`, `12s`, `1m 05s`; labels and the formatter live in `run-labels.ts`, shared with the panel); a failed row carries the reason under its name and a waiting run reports `—` rather than a duration it has not finished. Pages are 25 runs: the list fetches the next ones itself as the sentinel scrolls into view, up to three pages (`run-pager.ts`, `use-run-pages.ts`), and then asks with "Load older runs" — scrolling should not quietly pull a thousand rows. A run that arrived on two pages is kept once, and a list that has moved on since it was rendered starts again rather than showing a stale first page. Empty states name the case: no runs at all, none for this flow, none with that status, or none older than the page reached.

`@panel/[id]` loads the run and shows it in the panel: the status badge, trigger source, start time, duration and an "Open on canvas" link, then the Trigger section (the node that fired and its payload as JSON), the run-wide error when the engine reports one, a Steps section with every node in execution order as a native `<details>` row (catalog icon and label, status, elapsed; failed and waiting rows start open) holding the outputs per handle as JSON, explorer links for transaction hashes, the error text, or the "Auto-answered" marker, and a Variables section with the final `vars` when there are any. A run the user does not own renders not-found.

## Flow builder

Below 1024 px the builder keeps both 45 px rails and overlays one panel at a time above the canvas, below the actual wrapped toolbar. Panels start closed; sidebar and right-rail controls open them, selecting a node opens its settings, and Close or Escape dismisses the panel and restores its opening focus target. The run header wraps and run details stack on narrow screens. Desktop panels retain their 260 px and 360 px widths.

`/flows/[id]` renders the builder edge to edge: a permanent 44 px sidebar on the left edge, a 260 px panel beside it, a middle column with a 44 px header above the React Flow canvas (on the left a Simulate/Live segmented control and the run button — **Run**, or **Run live** as a filled button in live mode — joined by Stop and Restart icon buttons only while a run is in flight, then Undo and Redo icon buttons and, when the flow has any, a problems chip; on the right a Commands button, a secondary Save button and an outline Share menu whose two items open the mini-app share dialog and the marketplace publish dialog), and a 360 px panel docked on the right that minimizes into a 44 px rail on its edge. Every bar shares one rhythm: 44 px of content plus a 1 px border outside it, an 8 px inset, and 28 px ghost icon buttons (Coss `icon-sm`) with 4 px between them, so every control lands on the same pixel row. The panel title rows, the canvas header, the sidebar, and the rail all use it, so the top rows line up and a rail's first control sits on that same row; titles are caption-size medium type. Tooltips on Run, Save, Undo, Redo and Commands name their key as well, formatted for the reader's platform by `lib/shortcuts.ts`. There is no breadcrumb yet; the visual design is being redone from this reduced state.

The canvas draws nodes from the catalog in `apps/web/src/builder/catalog.ts`: 44 types in eight categories (Triggers, Logic, Data, Onchain, AI, Screens, Notifications, Integrations). Every type except `logic.for-each` (which the engine runs itself) has an executor in the engine, and every type with settings has a config schema in `packages/contracts` (see Node settings below; `world.verification-completed` and `privy.wallet` take none). Type ids are `<kind>.<name>` for core nodes and `<provider>.<name>` for integrations (`world.*`, `privy.*`, `usdc.*`, `graph.*`); a provider's trigger, such as `world.verification-completed`, is a trigger by category. Node cards use singular category names in the eyebrow, while the palette's headings use plural form. Every type declares named ports: triggers have no inputs, several types take two, branching types such as If/else have two outputs, and every type has at least one output. A card is a header plus a two-column grid of 24 px port rows, one handle per row, and an edge records the port it uses as `sourceHandle` and `targetHandle`. Edges are orthogonal (`smoothstep`). The palette adds a node on click (viewport centre, through `useAddNodeAtCenter`) or drag (pointer position, through the `application/x-automator-node-type` MIME type). Connections reject self-loops, duplicates, a second edge into an already-occupied input, and cycles. Delete/Backspace removes the selection, Shift-drag box-selects, a bottom-left panel zooms, fits the view and tidies up (moves every node onto the left-to-right grid of `packages/contracts/src/flow-layout.ts`, the same layout the AI generator uses, as one undo step), and a minimap sits bottom-right while the canvas has nodes. An empty canvas shows a note that every flow starts with a trigger, with a button that adds the mini-app trigger. A getting-started checklist (`getting-started-panel.tsx`, top-right over the canvas) shows until dismissed: connect a trigger to a node, save, simulate, activate or publish, each ticked from builder state (`getting-started.ts`: an edge exists; built and not dirty; a run is on the canvas; triggers enabled or a listing exists) with a progress bar; Dismiss, or Done once every step is ticked, sets the `builder_checklist` cookie that the canvas page reads. The canvas shortcuts live in the hotkey registry's `canvas` scope (`use-canvas-hotkeys.ts`, mounted by the canvas header): Cmd/Ctrl+Z undoes and Cmd/Ctrl+Shift+Z redoes, Cmd/Ctrl+S saves, Cmd/Ctrl+Enter simulates, and Cmd/Ctrl+D duplicates the selected nodes with the edges between them, offset by 40 px and selected. Undo and duplicate stay quiet while typing in a field. Open dialogs suspend background canvas shortcuts, including through nested portals; IME composition never triggers them, and Cmd/Ctrl+S still suppresses the browser Save Page dialog. React Flow's attribution and minimap are hidden.

Dropping a connection on empty canvas opens a node picker at that point (`node-picker.tsx`): a search box over the whole catalog, filtered to the nodes that can accept the connection (a trigger has no input, so it never appears), arrow keys and Enter to pick, Escape or a click outside to dismiss. The picked node arrives already wired to the port the drag started from, and one undo removes the node with its edge.

⌘K (Ctrl+K) opens the command menu (`command-menu.tsx`): one list over the flow's own actions — Run flow or Run live, Save, Undo, Redo, Fit the flow in view, Flow settings, Share as a mini app, Publish to the marketplace — plus the account's saved nodes and, once something is typed, the node catalog. Picking a node adds it in the middle of the canvas. The menu itself is one of the dialogs `builder-dialogs.tsx` mounts once and tracks, so the header's Commands button opens it too; the sidebar's Flow settings button and the header's Share menu use the same provider.

The side panels sit on the card surface, one step above the canvas in both themes. The sidebar's header slot holds a "Leave flow" icon link back to `/flows` under the same line as every other header. Below it, one ghost icon toggle per panel section (the active one shown pressed) picks what the left panel shows: Nodes (the catalog), Variables (the user's secrets by name, see below), Outline (a node list with search for large canvases), and History (`flow-history.tsx`: the flow's saved versions newest first, `v<n>` with time and node count and a Current badge on the newest, fetched when the section opens and after every save; Restore loads that version onto the canvas through `applyDocument`, so it is undoable and marks the flow unsaved, and a note reads "Restored v<n>. Save to keep it." until the next save); and a separate "Flow settings" icon button pinned to the bottom opens the flow settings dialog. The left panel's title row shows the flow name as `h1`, with a small muted flow icon before it. Under Nodes the body is the node palette, a two-level catalog. Its resting state is the group list: a "Core" section with one row per kind (Triggers, Logic, Data, Onchain, AI, Screens, Notifications) and an "Integrations" section with one row per provider (World, Privy, USDC, The Graph), each row showing an icon or logo, a description, and the node count. Opening a group replaces the list with that group's entries under a "‹ All" back control and the group name; a provider's entries split into Triggers and Actions sections, so a provider's own trigger lives with its actions rather than under Core › Triggers. The search box above (matching labels and descriptions, case-insensitively) wins while it has text and shows flat results sectioned by group across the whole catalog; clearing it returns to wherever the palette was. A grid-view toggle beside the search switches node lists between rows (icon, label, one-line description) and three-per-row tiles (description in a tooltip). No match shows "No nodes match." with a Clear search link. Groups are declared in `catalog.ts` (`catalogGroups`, each entry carries a `group`), and the three views are the pure functions `listCatalogGroups`, `getCatalogGroupSections`, and `searchCatalog`. Search, open group, and view are component state and reset with the page. Outline (`flow-outline.tsx`) lists the flow's problems first (see below), then every node on the canvas with a search box; choosing either selects that node. The right panel's title row starts with a minimize control, and right-aligned Coss tabs (icon and label, 24 px tall in the 28 px list) switch between AI agent and Screen preview. Minimized, the panel becomes a right rail with one toggle per tab that reopens the panel on that tab. The state is not persisted.

The AI agent tab is a conversation about the flow (`apps/web/src/builder/ai-panel.tsx`). The thread lives in a per-builder zustand store beside the run store (`ai-store.ts`, mounted by `flow-builder.tsx`, never persisted, so loading another flow starts empty): user turns, assistant turns with the model's message or summary, and for each proposal its state. Messages render as a chat list with the composer at the bottom (Cmd/Ctrl+Enter or Send submits); an empty thread explains what a message does. Edit requests restore credentials only to retained nodes; replacement proposals never inherit credentials from matching old node ids. Every request sends the canvas as it is now, after any applied proposals, plus the thread's earlier turns as the contract's `history` (texts and summaries only), so "also notify Discord" edits the current flow. An "Edit the current flow" checkbox shows once the canvas has nodes, ticked by default, and unticking asks for a new flow instead; an empty canvas reads "New flow" and needs no choice. An answer is either a plain assistant message (a question or an explanation, when the prompt asked for no change) or a proposal: the summary with a preview card listing node by node what applying would do against the canvas right now (Keep, Change, Add, Remove, with label and type), plus added/removed connections and name, description or chain changes, and "Apply changes" (or "Replace canvas" when a new flow would replace nodes) puts it on the canvas through the store's `applyDocument`, which keeps the flow id, marks the flow dirty, and fits the view; Discard drops it. An applied turn reads "Applied", a discarded one "Discarded", and applying one proposal marks the other pending ones "Superseded by a later change", since they were drawn from an older canvas. "Start over" clears the thread (a request still in flight is dropped when it lands). Failures show as assistant turns in the thread: no OpenRouter key on the API, a session that expired, a prompt the model could not turn into a valid flow, or more than the API's per-user AI limit in a minute ("Too many requests. Try again in a moment."). Explanations of a failed run (see the run panel below) arrive in the same thread.

Screen preview plays the canvas as its mini-app (`packages/miniapp`) inside a phone frame sized from the panel's height, on the real flow engine: the nodes between screens execute in the author's browser, so clicking through a form wired to a Discord message sends it. A tools row above it, on the palette's rhythm, says whether the preview runs from the trigger or from the selected screen (selecting exactly one screen node opens the preview on that screen), a Restart icon button, and an "Open in browser" icon button that opens the runtime's `/a/[id]?preview` with only a random nonce in the fragment. The builder transfers a captured document directly to that exact window after verifying the runtime origin and nonce; the runtime verifies the configured builder origin and its actual opener. Reload works in the same popup while the builder remains open; a copied link cannot recover the document. Publish the mini-app to share a visitor link. Adding, removing or rewiring nodes restarts the session; editing a node's config, or the flow name shown in the phone's top bar, updates in place, and the next run uses the edited document. A flow without a mini-app trigger shows "Not a mini-app yet" in the phone. Because this is the author's own preview (as is the runtime's `?preview` page), a failed step shows the node's label and its real error text, which the author needs; visitors of the published app never see it, they get the generic failure screen with the trigger's visitor message (see Mini-apps in `docs/architecture.md`). The three identity screens (Privy login, World ID verify, World Selfie Check) render in the phone as they do for a visitor, but since neither Privy nor World can run against the author's session there, their button plays the node's sample answer and a note under it says so ("Preview: continues as visitor@example.com", "Preview: continues as verified"); a World node's `simulate` setting picks the branch.

The Variables section (`variables-panel.tsx`) lists the signed-in user's secrets as `{{secrets.<name>}}` with a delete control, and a form above them adds or replaces one (lowercase name, a password-type value that is never shown again); names are cached per signed-in account and cleared on identity changes; they load through the same-origin `/api/secrets` proxies into a small shared store (`secrets-store.ts`) that the node settings picker reads too. Form errors show under it, including "Too many requests. Try again in a moment." when the API's per-user limit on secret writes is hit.

Selecting one node swaps the left panel's palette for that node's settings (`node-settings.tsx`): the label, then one control per property of the node's config schema from `packages/contracts`, written to the store as it is typed, with a property's schema `description` under the control as help text. Enums are selects, booleans switches, numbers and strings inputs (prose keys such as body or content get a textarea), string arrays one comma-separated line, arrays of objects an item list (each item a bordered group titled by its label or id, with move up, move down and remove, and an add button that fills the item schema's defaults), and nested objects a group. Arrays of a fixed literal set, such as the agent's tools or the Privy login's allowed methods, are checkbox groups (`multi-select-field.tsx`). A string property marked `contentMediaType: "application/json"` in its schema — the triggers' **Sample payload**, a contract call's ABI and arguments, a subgraph query's variables — is a monospace JSON textarea: the text is stored as typed and an inline "Invalid JSON" note (with `aria-invalid`) appears while it does not parse. A media type ending in `javascript`, `typescript` or `graphql`, such as the Query subgraph node's **Query**, gets a taller monospace textarea with spellcheck off and no JSON check (`textFieldShape` in `schema-form/schema.ts`). Types without a schema only offer the label; the mini-app trigger offers a "visitor error message" that a published app shows visitors when it fails. The "Insert variable" menu lists, after the trigger's payload entry, one `{{trigger.<key>}}` per top-level key of the trigger's sample payload, expands an identity screen's answer into its fields (`{{input.<port>.email}}`, `{{input.<port>.nullifierHash}}`, …) and, below any Privy login, lists `{{vars.visitor.*}}`.

Node settings can be kept for reuse: Save node stores the label and config as a private preset (`save-preset-dialog.tsx`), and the palette lists them under Saved above the catalog groups, each row inserting an independent copy by click or drag with a delete control beside it. Secret fields are never stored, so a preset keeps a `{{secrets.name}}` reference and loses a pasted credential.

After a run, each string setting shows what its templates resolved to in that run under the control (`run-values.ts`, `use-run-preview.ts`): the path and its value, with `0`, `false` and empty text shown as themselves and an absent path reading "not set in this run"; secrets stay hidden. A line under the form names the run the values come from and says when the node's settings changed since, which makes that evidence stale.

State lives in a per-page zustand store; `serializeFlow` turns it into the `FlowDocument` contract and `hydrateFlow` reverses it. Simulate (`use-flow-run.ts`) runs the saved flow through `POST /flows/:id/runs` while the store is clean, so the run lands in the history, and falls back to the stateless `POST /flows/run` with the canvas document while there are unsaved changes; both requests explicitly select the starting trigger by node id and send its sample payload (`trigger-payload.ts`: the first trigger in document order without an incoming edge, its `samplePayload` config parsed through the trigger's schema, so an unedited sample is the default the settings show; `{}` for a blank sample or one that is not valid JSON) as the run's trigger payload and `screens: "auto"`, so a mini-app flow simulates end to end with every screen answered by the engine (pills read "Auto-answered", the run panel "Answered by Simulate · <port>", and a form's inspector shows the sample values), while the mini-app runtime keeps waiting for real visitors; the result lives in a separate run store (`run-store.ts`), which `?run=<id>` on the flow URL seeds with a stored run. A run the API refuses shows a message in the run panel's place: an expired session, a flow that no longer exists, invalid settings, or "Too many requests. Try again in a moment." past the per-user run limit. The page loads the stored document from the API and remounts the builder per flow id and run; an id the user does not own renders the canvas group's not-found screen. Save (`save-button.tsx`) serializes the store, sends it to `/api/flows/[id]` with the Privy access token, and calls the store's `markSaved` on success; it is disabled while nothing changed since the last save, shows a loading state while saving, a muted "Saved" afterwards, and an inline error message (session expired, flow missing, invalid document, or unavailable) when the save fails. The Flow settings sidebar button opens `flow-settings-dialog.tsx`, which edits the name, description and **Chain** (a select over the registry in `packages/contracts/src/chains.ts`: Base Sepolia or World Chain Sepolia, where the flow's onchain nodes read, write and listen) in the store (Apply) so that Save persists them like any other change; the chain lands in the document as `chainId`. Below them sit settings that are not document state: an **Active** switch that saves through `PATCH /flows/:id` straight away and lets the saved flow's webhook, schedule, onchain-event, price and balance triggers start runs, with the API's refusal shown as its own list of problems under it (and a note that the check read the saved flow, not the unsaved edits); the flow's **Webhook URL** (on the web origin, with a copy button) whenever the canvas has a Webhook trigger node; a per-canvas **Send real transactions** switch, mirrored by the header's Simulate/Live control, that runs onchain nodes live instead of as a dry run and turns the run button into a filled **Run live**; the first live run of a session is confirmed in an alert dialog naming the chain, and the mode resets to Simulate on reload; under it the embedded wallet's balances on the selected chain (`wallet-funds.tsx`, read once per chain per dialog open through the same-origin `/api/wallet` proxy: the shortened address, the native and USDC amounts, and the warning "This wallet has no funds on <chain>." when both are zero; no faucet link); and the Server signing control. A flow that carries signer nodes is held back until the wallet can sign: `useWalletSigning` reads `GET /wallet` when the dialog opens, and while it answers `signing: false` the Active switch is disabled over a line naming the nodes ("Send USDC and Sign message need server signing, which is off for your wallet"), which the Server signing control below clears. The mini-app share dialog holds Publish app the same way, with `EnableSigningButton` beside the warning. Neither is held while the API reports no signer at all, since then only a run can tell. Activation and the webhook token reach the builder through `flow-activation.tsx`, seeded from the loaded record. The save controller is created once per builder (`SaveFlowProvider` in `save-button.tsx`) and shared by the Save button, Cmd/Ctrl+S and the unsaved-changes guard (`leave-guard.tsx`, decisions in the pure `leave-decision.ts`): while the store is dirty a `beforeunload` handler makes the browser ask before the tab closes, reloads or leaves for another site, and a plain click on an in-app link away from the canvas (the sidebar's "Leave flow", the publish dialog's "View listing") opens a Coss alert dialog, "Leave without saving?", with Stay, Leave (navigates without saving) and Save and leave (runs the shared save and navigates only when it succeeds; a failure shows its message in the dialog). Modified clicks that open a new tab pass through and a clean store navigates straight away. Browser Back and Forward use the same dialog for cancelable same-document traversals through the Navigation API: Stay leaves the current entry and Next.js history metadata untouched, while Leave or a successful Save and leave resumes the original entry by key, without adding history entries. Browsers without this API, and traversals the browser makes noncancelable (including anti-trapping overrides), cannot show this custom guard; cross-document exits retain the native beforeunload prompt. Creating or forking a flow uses POST server actions; GET `/create` only offers the creation control. Example documents come from the hand-authored fixtures in `examples.ts` (`exampleToFlowDocument` copies them with fresh ids).

The store keeps an undo history (`past`/`future`, capped at 50 entries): every document change opens an entry, a drag counts as one, deleting a node with its edges counts as one, consecutive edits to the same label, config field or flow setting coalesce, selection never enters history, loading a document clears it, and applying an AI result is undoable. Undo and redo mark the flow dirty.

Validation runs on every change (`validation.ts`, through `use-flow-problems.ts`): the contract's referential checks, a missing or unreachable trigger, nodes no trigger reaches, config the engine cannot read, config it refuses to run without (a variable name, a Discord message, a World action id), an empty form, a trigger sample payload that is not valid JSON (a warning: Simulate sends an empty one), and a World ID verify whose Rejected port is unwired (a failed verification would then end the flow as done). A blank secret such as a forked Discord webhook is a warning that reads "set your own". Cards show a badge (red for errors, amber for warnings) that is a focusable control listing its node's messages in a Coss tooltip, and an error tints the card border; the Outline lists every problem. The canvas header carries a chip counting every problem in the flow, tinted for the worst severity, whose menu lists each message with the node it belongs to and selects and centres that node when picked. The run button always runs.

After a run, the canvas shows the result in place: each node's status pill carries its elapsed time, edges that fired turn green and the ones that went dead are dashed and faded (`run-selectors.ts`), and a run panel (`run-panel.tsx`) docks to the bottom of the canvas with the run's outcome, total time, the trigger that started it, and the run-wide error the engine reports (for example a flow with no trigger), then every node in execution order with its status and elapsed time. Choosing a row selects the node on the canvas and shows its outputs per handle (an output carrying a transaction hash, such as a receipt, gets a "View on <chain>" link to the flow's chain explorer above the JSON), its error (with an "Enable server signing" button when the error says signing is not enabled, and the same "This wallet has no funds on <chain>." warning as the settings dialog when the error says the wallet could not pay), or why it was skipped; a screen that Simulate answered reads "Auto-answered" on the card and "Answered by Simulate · port" in the row; the panel opens on the failed node when there is one, can collapse to its title row, and clears with the run. A failed run offers "Explain with AI" in the title row and under the failed node's error (`use-explain-run.ts`): it posts the canvas document with its secret config fields blanked (`redactFlowSecrets`) and the run's results with outputs, errors and trigger payload passed through `redactRunOutputs` to `POST /ai/runs/explain` through the same-origin proxy, adds the question to the AI thread, and brings the AI tab in front; the answer lands there as an assistant message, or as a message with a proposal card and Apply when the model proposes a config or wiring fix. React Flow's own colour mode is unused; the builder tokens restyle it in both themes through `flow-builder.module.css`.

## Marketplace

`/marketplace` browses every published flow together with the eleven curated examples. It is the second workspace page with no title bar: like Home it names itself in the middle of its own 1040 px column, and everything under the head answers to that column as a container query rather than to the viewport, so the sidebar's state changes the layout without a media query. The head is centred — the title, one sentence on what the page holds, a search field (matching name, description, author, node type ids and category names), and a row of category chips (All, then Mini-apps, AI, Onchain, Notifications, Logic derived from each listing's node types; a listing can be in several) each carrying its count. The one control that is not part of that column keeps the top-right corner: "Publish a flow", a menu of the reader's own flows that opens each at `/flows/<id>?publish=1`, or a link to `/flows` when there are none.

The page has two states. Its resting one is a storefront: the editorial pick (`featuredSlugs` in `marketplace/curated.ts`, resolved by `featuredListing` against what is actually published, with a fallback so the page always leads with something) in a wide block with the flow drawn large, Fork flow and Read it, then the sections `listingSections` returns — Yours, only once you have published; From the community; By Automator — each with its count and a "See all" that scopes the catalog to it. Touching search, a category or a scope turns the page into the catalog: the same head over a count, a sort menu (Newest, Most forked, Name A–Z) and one list. Every control reads from the URL (`q`, `show`, `category`, `sort`) and writes back through `history.pushState`, which Next syncs with `useSearchParams` without re-running the server component, so a filtered view can be linked and navigated back to; typing replaces the entry instead of pushing one.

A listing is a row card in a two-column grid that becomes one column under 720 px: the flow's own miniature drawn from the listing's outline (`flows/flow-miniature.tsx`, the same drawing a flow card on `/flows` uses), then the name linking to the detail page, the description, an author line with a `DitherAvatar` generated from the username — the product mark for Automator — and the one signal a listing can honestly carry, its fork count or an "Example" badge. Fork is hidden with opacity until the card is hovered or focused, so it keeps its place in the tab order. Empty states name the situation: no matching search or scope, with a "Back to the marketplace" button, and a community section with nothing in it invites the reader to publish instead. Sorting by newest puts published flows before the undated curated examples; the browse logic is the pure `browseListings`, `featuredListing` and `listingSections` in `apps/web/src/marketplace/listing.ts`.

`/marketplace/[slug]` shows a curated example or a published listing in a reading column under the frame's breadcrumb back to Marketplace, with Copy link and Fork flow on the title bar: node marks, the same author line the cards carry (with the publish date and fork count for a published flow), the description, a read-only React Flow preview of the graph (`apps/web/src/marketplace/flow-preview.tsx`: pan and zoom only, the builder's node cards), and a numbered "How it works" list. For published flows the steps are the document's non-trigger nodes, named by their labels and described by their catalog entries. Unknown slugs return not-found. Forking a curated example goes through `/create?example=`; forking a published flow goes through `/marketplace/[slug]/fork`, which asks the API for a copy and redirects to the new `/flows/[id]`.

Publishing happens from the builder's Publish button, or from the marketplace's "Publish a flow" menu, which opens the same dialog on the chosen canvas through `?publish=1` and strips the parameter once it has (`builder-dialogs.tsx`), so a reload does not reopen it. The dialog loads the flow's current listing first, then offers "Publish to the marketplace" for a new one or "Update listing" (with an Unpublish action and an inline confirmation) for an existing one. It edits a listing name (up to 120 characters) and a description with a 280-character counter, warns when the canvas has unsaved changes because the listing is made from the last saved version, and on success shows Copy link and View listing. Failures name the cause: an expired session, an unfinished profile, a flow that no longer exists, or invalid input.

## Placeholders and dev tooling

`/settings` and `/mini-apps` are placeholder routes that say what has not moved yet: settings still open as a dialog from the account menu, and mini-apps are shared from the builder rather than listed. The workspace shell does not fetch API health to render itself. Agentation is available in development only, using the same local annotation setup as UI Lab.

Run results retain the executed document snapshot for labels, explanations and explorer links. Historical node rows remain inspectable after the corresponding canvas node is removed. Clear run is disabled while a request is active; Stop, restart and unmount cancel obsolete work, including requests still waiting for authentication. A completed save only marks its captured document as saved, so later edits remain dirty. Pending version restoration cannot overwrite intervening edits or apply after History closes.
