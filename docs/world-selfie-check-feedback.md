# World Selfie Check (Beta): integration feedback

Written while adding the `world.selfie-check` screen node to Automator on 2026-09-10, for the ETHOnline 2026 "Selfie Check" track. Automator is a visual flow builder; a flow published as a mini-app runs on `https://run.automator.ardasari.co/a/<flowId>`, and the node pauses that mini-app until World App answers. The app already had a World ID 4.0 relying party (`IDKitRequestWidget` with a signed `rp_context`, proofs verified on `POST /api/v4/verify/{rp_id}`), so this document is mostly about what it took to add the Selfie Check credential next to that. Versions: `@worldcoin/idkit` 4.2.3 (`@worldcoin/idkit-core` 4.2.4), `@worldcoin/idkit-server` 1.1.1, `@worldcoin/minikit-js` 2.0.3.

## 1. Selfie Check documentation and integration flow

**What worked.** The IDKit credentials page (`docs.world.org/world-id/idkit/credentials#selfie-check-beta`) gives the one thing that matters: the `selfieCheckLegacy({ signal })` preset, requested through the same `IDKit.request({ app_id, action, rp_context })` call as every other credential. Because our runtime already built presets as plain data (`{ type: "DeviceLegacy" }`, `{ type: "ProofOfHuman" }`), adding `{ type: "SelfieCheckLegacy" }` was a one-line change in the request path and no change in the verifier's transport. The credential page (`docs.world.org/world-id/credentials/11`) is clear about what the credential means: medium assurance, liveness plus face similarity, no Orb, valid 90 days, "a proof of the completed check, not a numeric Sybil or uniqueness score". That sentence is what let us position the node honestly as a fairness and abuse-prevention gate instead of proof of uniqueness.

**What was confusing.**

- The IDKit page says "The preset currently uses World ID 3.0; World ID 4.0 support is not yet available." We first read that as "this cannot go through the 4.0 request/verify path", which would have meant a second, legacy verifier (`verifyCloudProof` against `/api/v2/verify/{app_id}`). It actually means the credential is a 3.0 credential and the result comes back as a `protocol_version: "3.0"` `IDKitResultV3`; the request still goes through the signed `rp_context`, and `/api/v4/verify/{rp_id}` accepts it when the request set `allow_legacy_proofs: true`. One sentence on that page ("requested through the 4.0 request, answered as a 3.0 result, verified by the v4 endpoint") would have saved the investigation.
- Neither page says what the credential is called in the result. We had to read `idkit-core`'s type definitions to learn the response item's `identifier` is `selfie` (`issuer_schema_id: 11`), and the source to learn that IDKit rewrites World App's `face` to `selfie` (`normalizeLegacyResponseIdentifier`). Server-side verification needs that name to know the portal verified the credential that was asked for rather than another one in the same result, so it belongs in the docs next to `proof_of_human` and `device`.
- The credentials page never says which server endpoint verifies a Selfie Check result, and the sandbox page does not either. We assumed the v4 endpoint from the `rp_context` requirement; a line confirming it, with the shape of the `results[]` entry for a selfie credential, is missing.
- The three pages use three names for the same thing: "Selfie Check (Beta)", "Selfie Check-compatible World ID credential flow" (track page) and, in code, `selfieCheckLegacy` / `SelfieCheckLegacy` / `selfie` / `face`. A short glossary would help.
- "Request access to enable Selfie Check (Beta) for your app" has no link and no description of where the granted state shows up (see section 2).

**Integration flow, as built.** Screen config: title, message, button, portal `action`, optional `signal` template, and which branch Simulate takes. The API signs a request for the action when it serves the screen, the browser asks IDKit with the `SelfieCheckLegacy` preset, the result is posted back to the API bound to that session's nonce and expiry, the API forwards it to `/api/v4/verify/{rp_id}` and continues on `verified` with `{ verified: true, nullifierHash, credential: "selfie", action }` or on `rejected` with `{ verified: false, code, detail }`. That shape lets a following condition node gate a USDC payout on `verified`, which is the "one live person, one payout" use we ship as a curated example.

## 2. Developer Portal: navigation, search, product discovery, debugging guidance

- **There is no Selfie Check toggle or status anywhere in the portal.** For app `app_f1db1520f31ffc3fa6022d255960dbfb` (team "automator") we checked the World ID Dashboard (actions tab) and the World ID Configuration tab (`/world-id?tab=configuration`, which shows App ID, RP ID, signer address, key rotation and the danger zone), and the developer-portal MCP's `get_app_config` output (app metadata, `rp_registration`, `actions_v4`, verify/proof-context/status endpoints). None of them says whether Selfie Check (Beta) is enabled for the app. The only place the granted state can surface is World App itself at request time, as a `credential_unavailable` or `feature_unavailable` IDKit error. Access was requested and reportedly granted for this app; we could not confirm it before building and cannot confirm it without a phone. A "Beta features" line on the World ID Configuration tab, with the same flag exposed by `get_app_config`, would fix this.
- **Where do actions live for a managed 4.0 RP?** After switching the app to a managed World ID 4.0 relying party the Dashboard's action list is empty and `actions_v4` is `[]`, while the IDKit request still takes an `action` string. It is not clear from the portal whether a Selfie Check action must be created in the portal first (as for Incognito Actions) or whether any action string signed by the RP key is accepted, and whether a legacy (3.0) credential inside a 4.0 request needs a portal action of the legacy kind. Our node tells the builder to paste "the action id from the World Developer Portal" because that is what the older docs said; we could not verify it for Selfie Check.
- **Navigation.** The World ID section is a single page with `?tab=` state (`?tab=actions`, `?tab=configuration`); deep links to a tab are not discoverable (guessing `/world-id/configuration` gives a bare Next.js 404 page). The left sidebar's "World ID Configuration" is a tab switch, not a route, so the browser's back button and shared links behave unexpectedly.
- **Product discovery.** Nothing in the portal points from the World ID configuration to the credentials that can be requested (Orb, Device, Document, Selfie Check), nor to IDKit's preset names. The sidebar card "World ID Sandbox: Install the test build" is the only sandbox entry point and does not say whether the sandbox build supports Selfie Check.
- **Debugging.** The portal offers no log of verification attempts for a 4.0 RP (the v4 `rp-status` endpoint exists but is not surfaced), so a failed verification can only be debugged from the client's IDKit error code and the verify endpoint's JSON. The `verify_endpoint`, `proof_context_endpoint` and `status_endpoint` fields in `get_app_config` are useful and should also be visible on the Configuration tab.
- **What worked.** The developer-portal MCP is a good idea: `get_team_context` and `get_app_config` answered in one call what would otherwise be several screens. The Configuration tab's copy buttons for App ID, RP ID and signer address are exactly what an integrator needs.

## 3. Sandbox: app states, proof flows, test users, errors, edge cases

- The sandbox page (`docs.world.org/world-id/sandbox/testing-selfie-check`) is well structured: hot, cold and semi-cold user states, native versus web entry surfaces, and the known limitations (unlisted sandbox apps behind TestFlight or private Play links, iOS semi-cold recovery limits, platform-specific invite codes). It sets expectations correctly that a real test needs a phone with the sandbox World App.
- It does not say how a relying party selects the sandbox: our request carries `environment: "production" | "staging" | "sandbox"` and our verifier refuses a proof whose `environment` differs from the API's configured one, but the page never mentions the `environment` field, whether `sandbox` proofs verify on the same `/api/v4/verify/{rp_id}` endpoint, or whether the RP must be registered on a sandbox network (the portal shows only `status` and `staging_status` for the RP).
- There are no documented test users or fixtures. A relying party cannot unit-test its verifier against a known-good Selfie Check result because no sample `responses[]` entry for `identifier: "selfie"` is published, and the sandbox cannot be driven from CI. We stubbed the verifier in tests and hand-wrote the result shape from the type definitions; a published sample result (3.0 and, when it arrives, 4.0) would let integrators test the full server path.
- Edge cases we had to decide ourselves: what a result with a successful `proof_of_human` but a failed `selfie` entry means (we reject it as a level mismatch), what a 408/429 from the verify endpoint means (we treat it as "unknown, retry" and never take the rejected branch on it), and how the 90-day validity shows up in a result (the docs say re-verification is needed after inactivity, but the result has no expiry for the 3.0 credential).
- Error strings we mapped from `IDKitErrorCodes` for visitors: `credential_unavailable`, `feature_unavailable`, `verification_rejected`, `max_verifications_reached`, `nullifier_replayed`, `rp_signature_expired`, `timestamp_too_old`. The docs do not say which of these a Selfie Check specifically produces when the app is not enabled for the beta, when the visitor fails liveness, or when the visitor's 90-day credential has lapsed; a table would help.
- The sandbox page's "Next steps" is "contact your World point of contact". Hackathon teams do not have one.

## 4. What was confusing, missing, broken, or hard to test

- **Confusing:** the "3.0 only, 4.0 not yet available" sentence (see section 1); three names for one credential; whether an action must exist in the portal for a managed 4.0 RP.
- **Missing:** the credential name in results (`selfie`) and the `face` alias; the verify endpoint for a Selfie Check result; any portal indication that Selfie Check is enabled; a sample result for server-side tests; the `environment` field in the sandbox docs; a list of the IDKit error codes a Selfie Check can produce and when.
- **Broken:** nothing we could prove broken without a phone. The portal's bare 404 for a guessed deep link is a small paper cut.
- **Hard to test:** everything past the QR code. The integration can be exercised with unit tests (contracts, engine Simulate, mini-app preview, API verifier and session routes with a stubbed verifier), but the one thing the track is about, a live selfie, needs a phone with the sandbox or staging World App, a published mini-app URL, and the beta flag we cannot see. A web-based simulator for the credential, or a "test result" button in the portal that emits a signed sample result for the RP, would turn a half-day of blind building into a ten-minute check.
